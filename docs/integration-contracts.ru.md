# Контракты интеграции netDM

P1 реализует служебный IPC для тестового мира и режима Observe. Границы следующих этапов опираются на [диздок](integration-design.ru.md).

## IPC V1.0

- Host и bridge запускаются с `NETDM_IPC_MODE=v1`. Windows использует `NETDM_PIPE_NAME` (по умолчанию `netdm-core`) и доступ текущего пользователя. На Linux используется абсолютный `NETDM_SOCKET_PATH` (по умолчанию `/run/netdm/core.sock`) внутри заранее созданного каталога, доступного владельцу и доверенной группе. Права сокета `0660`. Host удерживает `flock` на `<socket>.lock` до закрытия listener. При перезапуске он заменяет только сокет того же UID, на котором `connect` вернул `ECONNREFUSED`, и повторно сверяет inode перед удалением. Живой listener, обычный файл и symlink оставляет на месте. Оставшийся lock-файл используется следующим Host.
- Кадр состоит из `uint32` big-endian и ровно указанного числа байтов UTF-8 JSON. Длина от 1 до 49 152 байтов проверяется до выделения тела. Некорректная длина и неполный кадр закрывают соединение. На Hello даётся 5 секунд, на следующий кадр владельца 30 секунд. Диспетчер должен регулярно посылать запрос, например опрос квитанций, даже в тихом раунде. Один `pump()` только читает входящие ответы.
- Первый кадр содержит `op=hello`, `protocolMajor=1`, `protocolMinor=0`, `serverId` и UUID `roundEpoch`. Host возвращает `session.ownerFence`, `streamId`, максимальный размер кадра и `nextSequence="1"`. `serverId` идентифицирует источник в контракте. Право доступа определяется локальным ACL и lease соединения.
- Последующие запросы содержат `ownerFence`, текущий `streamId` и строковый `commandSequence`. Host сверяет последовательность до диспетчеризации и отклоняет повтор или пропуск как `sequence_mismatch`. Это защита от повторной диспетчеризации в рамках соединения. Результат потерянного ACK выясняется через resync. Хеш запроса и воспроизведение сохранённого результата относятся к следующим контрактам.
- ID узлов, пакетов и курсоры представлены десятичными строками. V1 сериализует все `long`/`ulong` как строки. В пределах одного `streamId` выделенный ID узла повторно не регистрируется даже после удаления. Лимит истории выделенных ID составляет 65 536. Полноценное отображение `{endpointId, generation}` на мир появится вместе с DM lifecycle.
- `game_reset` заменяет игровой runtime целиком и возвращает новый `streamId` в рамках текущего owner lease. Смена раунда требует нового соединения с новым `roundEpoch`. Отложенные вычисления используют прежний runtime, а поздние ответы несут прежний `streamId`. Disconnect отзывает lease, отменяет его ожидающую работу и сбрасывает transient state. Следующий владелец начинает с пустого графа.
- `packet_send` принимает теги корреляции и размер пакета. `submission.accepted` означает admission в Host. `packet_receipts` возвращает до 32 записей в V1. Квитанция `Delivered` означает прохождение моделируемого транспорта. `Applied` и отдельный application ACK появятся с typed effects. Служебная квитанция никогда не запускает игровой эффект напрямую.
- Bridge хранит до 256 исходящих и 1024 входящих буферов. При V1 overflow он закрывает старое соединение и отбрасывает старые ответы. DM игнорирует ответы вне своего потока, снимает зависший poll по таймауту и просит resync при пропуске квитанций. `netdm_reconnect` инициирует смену соединения. `netdm_shutdown` присоединяет worker и используется при остановке мира.
- Управление потоком. Worker bridge за итерацию отправляет до 32 кадров и читает до 64 блоков по 4 KiB. Он спит только при отсутствии прогресса. Таймаут неполного кадра отсчитывается от последнего завершённого кадра. Host читает команды независимо от записи ответов. Ответы соединения проходят через очередь до 256 кадров и 2 MiB, а отдельный writer объединяет их в запись до 64 KiB. Windows pipe создаётся с буферами по 64 KiB. Если peer перестал читать и очередь заполнена, Host закрывает соединение. DM восстанавливает сессию через новый Hello и snapshot.
- Отказ packet или reroute worker сразу делает game readiness ложной и закрывает admission. Затем Host завершается с кодом 70. В Compose его перезапускает `restart: on-failure`. Windows launcher перезапускает Host до пяти раз за десять минут. Работающий DreamDaemon проходит тот же путь reconnect и snapshot, что и после аварии Host.
- Windows и Host сохраняют `NETDM_IPC_MODE=legacy` по умолчанию для существующих JSON-lines клиентов разработки. Доступный Linux bridge использует V1. Для воспроизводимого запуска задайте режим явно в обоих процессах.

```json
{"id":"dm-1","op":"hello","protocolMajor":1,"protocolMinor":0,"serverId":"station-test","roundEpoch":"9606dce0-4396-4d6f-a016-0739f5604088"}
```

## IPC 1.1 и публикация world snapshot

Клиент выбирает `protocolMinor=1` в Hello. После Welcome сессия ждёт snapshot. Версия 1.0 остаётся совместимой с клиентами разработки.

1. `snapshot_begin` объявляет `snapshotId`, `chunkCount`, `factCount` и строковый `factSequence` для базового среза. Действует лимит 512 chunks, 32 768 фактов и один staging runtime на владельца.
2. `snapshot_chunk` передаёт `snapshotId`, последовательный `chunkIndex` от нуля, JSON-массив в строке `factsJson` и его MD5 в hex. До 128 записей `add_node` с координатами, `connect` или `game_radio` на chunk. В `snapshot_commit` клиент передаёт MD5 от конкатенации верхнерегистровых digest по порядку. Host сверяет количество, ссылки и дубликаты и строит отдельный runtime.
3. `world_delta` догоняет изменения по `snapshotId` и строковому `factSequence`, увеличивая его на один за принятый batch. Разрешены добавление, перемещение, удаление узлов и обновление роли транзита. Staging принимает до 4 096 таких фактов. Весь batch проверяется до изменения графа. Сохранение прежней позиции или роли считается допустимой операцией без изменений.
4. `snapshot_ready` с последним `factSequence` атомарно публикует snapshot вместе с catch-up deltas и возвращает новый `streamId`. До этого Observatory видит прежний граф, а приём игровых пакетов закрыт. После публикации `world_delta` продолжает ту же последовательность. Смена потока инвалидирует старые квитанции и незавершённые вычисления.
5. `heartbeat` подтверждает `snapshotId` и последний `factSequence`. `/api/readiness/ipc` возвращает `200`, когда endpoint слушает. `/api/readiness/network` возвращает `200`, когда snapshot опубликован, heartbeat моложе пяти секунд и packet/reroute workers работают: это условие приёма сетевой работы. `/api/readiness/game` дополнительно требует готового хранилища исследований (§17.4, см. P5). В остальных состояниях соответствующая проверка возвращает `503`. `/api/health` остаётся liveness.
   - Тело у `game` и `network` одно: `ready`, `networkReady`, `ipcReady`, `workersReady`, `heartbeatFresh`, `researchReady`, `research` (состояние хранилища), `phase`, `streamId`, `lastFactSequence`.
   - Приём сетевой работы (`packet_send`, `publish`, `invoke`, `discover`, квитанции) зависит только от `networkReady`. Сбой журнала исследований блокирует исследования, но не сообщения, радио и двери.
   - Compose проверяет здоровье `game` по `/api/readiness/game`: стек с непригодным томом исследований не считается поднятым. Windows-лаунчер следит за миром по `/api/readiness/network`: он останавливает мир при потере сетевой сессии, а о хранилище исследований только предупреждает.

`commandSequence` упорядочивает все IPC команды. `factSequence` упорядочивает только версии фактов. Невалидная delta сохраняет прежний граф и его `factSequence`. Неполный или неверный snapshot никогда не появляется в Observatory.

## P2: типизированные сервисы, доставка и application ACK

Операции работают только в staged-протоколе и только в опубликованном runtime. До публикации они отвечают `game_not_ready`, а `publish` дополнительно требует game readiness, как и `packet_send`. Endpoints, сервисы, подписки, доставки и inbox принадлежат runtime и сбрасываются вместе с ним при Hello, новом snapshot, disconnect и рестарте Host. После публикации snapshot DM заново сообщает свои локальные факты. Все 64-битные значения передаются строками, коды статусов — в `snake_case`.

| Операция | Смысл |
|---|---|
| `endpoint_attach {endpoint, generation, a}` | Endpoint на существующем узле мира (`unknown_node` иначе). Тот же ID с большей generation заменяет прежнего получателя и ограждает его доставки. После удаления принимается только большая generation. Бюджет в 65 536 ID на runtime включает удалённые записи. |
| `endpoint_detach` | Явное удаление. Удаление узла через `world_delta` каскадно удаляет его endpoints. |
| `service_register {instance, serviceType, schema, major, minor}` | Экземпляр сервиса от имени endpoint. Владелец экземпляра не меняется (`forbidden`). Неизвестная схема или minor получают `unsupported_schema`. При удалении владельца удаляются и подписки на экземпляр: подписчик не переходит молча к другому провайдеру. |
| `subscribe {key, instance, schema, major, projection, mode, maxPending}` | Подписка подтверждается только при совпадении schema и major с провайдером и известной проекции. Эвристического fallback нет. `mode`: `latest_value` или `queue` (глубина 1..16). Изменение параметров повышает `revision` и отменяет ещё не выданные доставки старой ревизии. |
| `publish {instance, producerSequence, payload, timeoutTicks, trafficClass}` | Payload проверяется по схеме. Получатели фиксируются в момент принятия. Каждый получает отдельную физическую доставку от узла producer к узлу подписчика. Повтор того же `producerSequence` с тем же каноническим содержимым возвращает прежний `messageId` без новых доставок. Другое содержимое даёт `idempotency_conflict`, меньший номер — `stale_sequence`. |
| `delivery_poll {afterSequence, limit}` | Неразрушающая страница inbox до 32 KiB. Запись остаётся до ACK, поэтому после потери ответа достаточно повторить poll. |
| `delivery_ack {acks:[{deliveryId, applied, reason}]}` | Application ACK. Повтор возвращает `duplicate` с прежним исходом. ACK доставки, которую DM не получал, — `invalid_request`. Неизвестный ID, например из прошлого runtime, ничего не меняет. |
| `delivery_status {deliveryId \| messageId}` | Диагностика состояний. |

Состояния доставки: `accepted → in_transit → transport_delivered → applied | rejected_by_world`. Терминальные отказы: `no_route`, `busy`, `expired`, `receiver_gone`, `superseded`, `cancelled`, `unknown`. Перед помещением в inbox заново проверяются generation получателя, ревизия подписки и срок. `latest_value` вытесняет ещё не выданное значение (`superseded`). Выданная, но не подтверждённая запись через 600 тиков после срока становится `unknown` и повторно не доставляется.

Отзыв доступа исключает подписчика из fanout и проверяется при приёме пакета и выдаче из inbox. После выдачи отзыв скрывает payload при повторном poll, сохраняя возможность принять ACK в пределах срока. Outbox ограничен 8 192 ожидающими отправками и пропускает отменённые записи при дренировании. Дедупликация DM хранит ограниченный кеш исходов и монотонную строковую границу обработанных `sequence` на runtime. Повтор после вытеснения исхода пропускается без ACK. Allowlist-обработчики синхронны.

Ограничения V1: payload схемы до 512 байт при общем пределе 8 KiB, fanout до 32 получателей (больше — `limit_exceeded` до принятия), до 16 подписок и 8 сервисов на endpoint, 8 192 активных доставки, inbox до 4 096 записей и 4 MiB, история 8 192 завершённых доставок. Отправку доставок в транспорт ведёт Host, не более 256 одновременно. Request ID с префиксом `svc:` зарезервирован, и `packet_send` его отклоняет. Первая схема — `atmos.sample` 1.0 с проекциями `full` и `panel.v1`.

DM-сторона в `dm/netdm_services.dm`:

- `/datum/netdm_endpoint_registry` выдаёт ID вида `e<n>`, уникальные в пределах раунда и не переиспользуемые. Они переживают переподключение к Host. Generation растёт только при `rebind` того же ID на другой объект. Игра переопределяет `make_ref` и `resolve_ref` на weakref, чтобы реестр не удерживал объекты.
- `/datum/netdm_effect_dispatcher` применяет доставку только через handler, зарегистрированный для схемы. Он проверяет `{recipient, generation}` через реестр и дедуплицирует по `deliveryId` в пределах runtime. При смене потока вызывается `reset_cursor()`.

### P2.2: command/result, политики и discovery

| Операция | Смысл |
|---|---|
| `endpoint_attach {..., domain}` | Домен — факт мира: станция, фракция, учебная зона. По умолчанию `station`. Смена домена при той же generation сразу учитывается политиками. |
| `service_register {..., discoverScope, subscribeScope, invokeScope}` | `none`, `domain` (по умолчанию) или `open`. Владелец всегда имеет доступ. Сервис, который запросившему не виден, отвечает `unknown_service`, как отсутствующий. Видимый, но запрещённый отвечает `forbidden`. Политика входит в регистрацию: другая политика под тем же экземпляром даёт `conflict`. |
| `invoke {instance, command, idempotencyKey, arguments, timeoutTicks}` | Команда контракта типа сервиса с типизированными аргументами. Ключ именует бизнес-операцию в пределах экземпляра. Тот же ключ, инициатор и аргументы не применяются второй раз (`duplicate`), другое содержимое даёт `idempotency_conflict`. Не больше 8 незавершённых команд на инициатора. |
| Inbox `kind=command` | Приходит провайдеру, когда пакет запроса физически дошёл. DM подтверждает его `delivery_ack` с `result`, который проверяется по схеме результата, или с отказом и `reason`. |
| Inbox `kind=result` | Отдельный пакет от узла провайдера к инициатору с `outcome` (`applied` или `rejected_by_world`), `reason` и payload результата. ACK инициатора фиксирует `ResultDelivered`. |
| `command_status {operationId}` | Только собственная операция инициатора и только коды. Payload результата приходит исключительно по сети. |
| `discover {serviceType, scanKey}` | Сетевая операция. Зонд идёт к каждому видимому по политике провайдеру типа (не больше 16), а Host от имени достигнутого провайдера отправляет назад `directory.descriptor`. Недостижимый провайдер в результатах не появляется. Повтор `scanKey` в пределах той же generation и типа возвращает те же операции. Смена типа под тем же ключом даёт `idempotency_conflict`. |

Исход операции и доставка результата учитываются раздельно. `outcome`: `pending`, `applied`, `rejected_by_world`, `not_applied` (запрос не дошёл до DM, это точно), `unknown` (DM получил команду, но провайдер исчез или не ответил; слепого повтора нет). `result`: `none`, `in_transit`, `delivered`, `failed`. Повтор `invoke` после потерянного результата заново отправляет записанный исход, не более трёх попыток, и команду повторно не применяет. Применённая команда с неверным или отсутствующим результатом остаётся `applied` с `result=failed` (`invalid_result`, `missing_result`).

Первый контракт команд — `machine.control/set_power`: аргументы `machine.set_power` 1 `{on}`, результат `machine.power_state` 1 `{on, changed}`. Команда идемпотентна: это `set_state`, а не toggle. DM кодирует boolean как `0`/`1`; каноническая форма схемы нормализует их в `true`/`false`.

`netdm_effect_dispatcher` получает `allow_command(serviceType, command, handler)` и `allow_result(command, handler)`. `/datum/netdm_command_handler/execute()` возвращает `list("result" = ...)` или текст причины отказа. Дедупликация по `deliveryId` распространяется на команды: повторная страница возвращает тот же ACK с тем же результатом.

Пока не реализованы: converters между версиями схем, capability-токены и права конкретных игроков сверх домена, broadcast accounting, durable журнал операций (в V1 ключи идемпотентности живут в runtime, их хранилище до 16 384 операций без вытеснения). Повтор после потерянного результата отправляет только плечо результата и не моделирует новое плечо запроса. Durable recovery операций относится к research ledger P5.

## P3.1 · начальный APC snapshot и транзит

В staged snapshot можно передать `area_span {area, x, endX, y, z}` и `area_apc {a, area, x, y, z}` вместе с `add_node`. Area ID и ID узла передаются строками. Span включает обе границы. Координаты `area_apc` обозначают обслуживаемую клетку, координаты `add_node` — корпус APC. Для одного APC разрешено по одной привязке на каждом Z одной обслуживаемой зоны. Физический Z APC должен входить в эти уровни. Перекрывающиеся spans и неверная привязка отклоняют commit. С 14.11.2026 у сегмента может быть несколько APC: каждый span принадлежит ближайшему к нему APC по клетке обслуживания, соседние span разных APC дают провод. Сегмент зоны, у которой нет APC на этом уровне, — пассивный короб: соприкасающиеся короба образуют один, и APC, касающиеся короба, соединяются минимальным остовным деревом по манхэттенскому расстоянию между клетками обслуживания. Устройства в коробе APC не получают. BlueMoon выгружает такие зоны с ID от `9900000000…` и все APC зоны; дополнительный APC привязывается к своей клетке, если она в его зоне.

Core строит связные сегменты внутри Z и выводит проводное ребро по общей стороне между двумя сегментами с APC. Если один APC обслуживает свою зону на двух уровнях, его локальные рёбра образуют путь между уровнями. Удаление этого узла снимает все его связи. Перемещение в пределах обслуживаемых Z сохраняет связи. Перемещение за их пределы требует новой геометрии и отклоняется в catch-up и live deltas.

В этом профиле APC по умолчанию пересылает пакеты, остальные узлы по умолчанию работают как endpoint. Факт `add_node` может явно задать `role: "endpoint"` или `role: "relay"`. `set_forwarding {a, role}` меняет роль в staged world delta без сброса сервисной сессии. Маршрутизаторы исключают endpoint из промежуточных hops, транспорт повторно сверяет роли перед hop. Для старых снимков без геометрии и без поля role сохраняется прежний transit default.

**Радиомосты APC (P7).** После проводных рёбер Host соединяет части проводной сети APC радиомостами. Для каждой пары частей на одном уровне Z берётся ближайшая пара APC; по этим кандидатам строится минимальный остовный лес с пределом 64 клетки (евклидово расстояние). Мост — ребро карты стоимостью 8, оно живёт по тем же правилам, что провод: есть, только пока оба APC активны, и пересчитывается при каждой перестройке карты. Учитываются только APC с обслуживаемым сегментом. `/api/game/status` отдаёт `apcBridges`: число частей до и после, длины мостов и разрывы до частей, оставшихся порознь.

### P3.2 · обновление карты в текущей сессии

BlueMoon передаёт начальный снимок с `profile="apc_map"`. Все его `add_node` принадлежат карте APC, включая узлы без обслуживаемого сегмента. Для live-обновления DM отправляет `area_update_begin {snapshotId, updateId, factSequence, chunkCount, factCount}`, затем `area_update_chunk {snapshotId, updateId, chunkIndex, factsJson, digest}` и `area_update_commit {snapshotId, updateId, digest}`. `factSequence` равен следующему номеру опубликованных фактов. Пока идут чанки, heartbeat использует прежний номер.

Host проверяет тот же manifest, геометрию, поколения ID и исходную последовательность. При commit он вычисляет разницу проводных рёбер, позиций и состава APC и публикует одним batch до 4 096 изменений. Незавершённый или отвергнутый update сохраняет активный граф и номер фактов. Успешный update сохраняет `snapshotId`, `streamId`, квитанции и сервисы живых узлов. Только удаление APC отзывает его endpoints. Если за время передачи принят другой world delta, commit устаревает. Новая транзакция может заменить незавершённую.

Обновление переносит целиком ограниченный набор фактов карты APC. По IPC передаются до 32 768 фактов порциями до 128 на кадр, BlueMoon использует чанки по 64. Host публикует только разницу графа.

### P3.3 · устройства: проводной порт или радио

Факт `add_node` карты APC может содержать `accessRange` (1..128). Тогда у APC есть радиоточка доступа на канале сети. Без поля точки доступа нет, значение `0` отклоняется. Вне фактов карты `accessRange` отклоняется. Две точки доступа никогда не связываются друг с другом, поэтому радио не соединяет несмежные зоны в обход их APC. Остальные правила радио прежние: общий канал и Z, взаимная дальность.

Устройство — любой сетевой объект кроме APC. DM сообщает о нём только факты мира в `world_delta` опубликованного runtime с картой APC:

| Факт | Смысл |
|---|---|
| `device_state {a, x, y, z, mount, anchored, range}` | Полное состояние устройства, все поля обязательны. Повтор того же состояния ничего не меняет. `x, y, z` — клетка, на которой объект фактически находится (для предмета в контейнере — клетка внешнего контейнера). `mount`: `fixed` или `mobile`. `anchored`: закреплён ли объект на этой клетке. `range`: радиус радио 0..128, `0` означает отсутствие радио. |
| `device_remove {a}` | Удаление устройства вместе с его endpoints, сервисами и доставками. ID больше не используется в этом потоке. |

Подключение выбирает Host. Закреплённое `fixed`-устройство на клетке сегмента, обслуживаемого APC, получает один проводной порт к этому APC. Устройство в другом острове той же зоны на том же Z (например, в баке за стенами) подключается к APC этой зоны. Если таких APC несколько, выбирается ближайший по клетке сегмента, при равенстве — с меньшим ID. Острова не добавляют связей между APC. Остальные устройства используют радио в пределах `range`: `mobile` даже в закреплённом состоянии, незакреплённые и находящиеся в зоне без APC на своём уровне. Без радио и без проводного порта устройство изолировано. Устройство всегда endpoint и не пересылает чужой трафик. DM не называет APC и не выбирает режим.

Пакет `world_delta` содержит либо только факты устройств, либо только сырые изменения топологии. Каждый принятый пакет увеличивает `factSequence` на один. Ответ перечисляет решения Host: `result.devices[] = {a, attachment: wired|radio|isolated, apc}`. Это диагностика, а не команда. Отказ не меняет граф и номер фактов. Отказывается: ID чужого узла мира, повторное или неизвестное устройство в пакете, повторное использование удалённого ID, `range` вне границ, превышение 4 096 устройств на runtime, сырое изменение узла устройства, факты устройств во время staging snapshot. Сырые lifecycle-изменения (`add_node`, `move_node`, `set_forwarding`, `remove_node`) не могут нести второй узел `b`.

Собственные изменения карты в одном коммите ограничены 4 096 рёбрами и узлами и 4 096 радиопрофилями. Производные переподключения устройств в этот бюджет не входят и ограничены числом устройств. Вся транзакция среды — не больше 16 384 изменений топологии и столько же радиопрофилей. Все проверки радиопрофилей выполняются до изменения графа с учётом no-op операций: профиль должен относиться к узлу, который существует после пакета. Узел, удалённый и добавленный в одном пакете, теряет прежний профиль.

Смена подключения публикуется одним снимком среды: старый порт снимается в той же публикации, в которой появляется новый, так что два пути одновременно не существуют. Коммит обновления карты пересчитывает все устройства относительно новой карты, включая точки доступа APC. Сырое удаление APC тем же пакетом переводит его проводные устройства на радио. Новый snapshot начинает runtime без устройств, DM сообщает их заново под новыми ID. Endpoint P2 можно прикрепить к узлу устройства.

DM-сторона BlueMoon — компонент `/datum/component/netdm_node` и `SSnetdm_observe` (см. `docs/netdm-observe.md` в BlueMoon). Подсистема отправляет факты пачками до 64, только между транзакциями карты и не больше одного запроса одновременно. Отказ пакета устройств запускает новую сессию.

### P3.4 · представление топологии для экрана

`topology_view {z, sinceVersion?, maxNodes?}` — ограниченное диагностическое представление одного уровня для владельца сессии. Кто увидит его в игре, решает DM: сейчас это только админский экран. Ответ `result`:

| Поле | Смысл |
|---|---|
| `version` | Версия снимка среды. Тот же `sinceVersion` даёт `{version, z, unchanged: true}` без списков. |
| `nodes` | `[id, x, y, flags]`, флаги: 1 транзит, 2 радио, 4 точка доступа, 8 устройство, 16 APC с обслуживаемым сегментом. |
| `edges` | Проводные связи `[a, b]` между показанными узлами. |
| `radio` | Радиосвязи устройств `[device, partner]`; пара устройств перечисляется один раз. |
| `truncated` | Список обрезан лимитом `maxNodes` (до 2 048) или размером ответа (40 KiB). |

До публикации runtime ответ `game_not_ready`. Представление только читает граф и не меняет номер фактов.

Экран BlueMoon — verb `netDM Topology` (Debug, право `R_DEBUG`) и TGUI-интерфейс `NetdmTopology` на PixiJS 8. Подсистема опрашивает Host только для открытых экранов, не чаще раза в секунду по кругу уровней, и отправляет окну данные только при новой версии. Окно не перерисовывается целиком: сцена применяет изменения по ID, сохраняет масштаб, сдвиг и выбор. После инициализации или отказа рендерера клиент присылает `act("renderer", {event: "init", backend | failure, initMs, nodes, dpr, agent})`, а когда сцена впервые получила непустой уровень, ещё один `act("renderer", {event: "drawn", backend, initMs, nodes, links, level, updateMs, dpr, agent})`; `initMs` в нём считается от открытия окна. Сервер принимает не больше 8 отчётов на окно, обрезает поля и пишет их в лог мира. Это технический отчёт о настоящем браузере клиента, не игровое действие.

### P3.5 · питание и исправность узлов

Узел передаёт трафик, только если у него есть питание и он исправен. Неактивный узел остаётся в мире: сохраняет ID, endpoints, сервисы и подключение, но не имеет связей. Восстановление возвращает те же связи без нового ID и без повторной регистрации.

| Факт | Смысл |
|---|---|
| `device_state {…, powered?, operational?}` | Состояние устройства входит в его полный факт. Отсутствующее поле означает `true`. |
| `node_state {a, powered, operational}` | Состояние узла карты APC. Оба поля обязательны. Узел должен быть живым узлом опубликованной карты. Повтор того же состояния ничего не меняет. |

Новый узел карты и новое устройство активны по умолчанию. Состояние узла карты сохраняется при обновлениях карты, пока узел остаётся на ней, и сбрасывается новым snapshot.

Последствия неактивности:

- APC теряет проводные рёбра к соседним APC и к своим устройствам, а также точку доступа.
- Закреплённое `fixed`-устройство за неактивным APC остаётся проводным и молчит: радио за него не включается. Это отличается от уничтоженного APC, после которого устройство переходит на радио.
- Неактивное устройство теряет провод и радио.
- Активное мобильное устройство рядом с неактивным APC может подключиться к другой точке доступа в радиусе.

`node_state` входит в тот же класс фактов, что `device_state` и `device_remove`: пакет `world_delta` либо содержит только факты, либо только сырые изменения топологии. Отказ получают: `node_state` для устройства, неизвестного или удалённого узла, без одного из полей, два `node_state` одного узла в пакете, смешение с сырыми изменениями. Отказ не меняет граф и номер фактов.

В `result.devices[]` добавлено поле `live`: подключение сейчас передаёт трафик. В `topology_view` добавлены флаги узла 32 «нет питания» и 64 «неисправен», а также список `down` — проводные связи `[a, b]`, которые существуют в модели, но молчат из-за неактивного конца: рёбра карты между APC и порты устройств. Версия представления растёт и при смене состояния без изменения топологии.

DM-сторона BlueMoon:

- Машина без питания: флаг `NOPOWER`.
- Неисправная машина: флаги `BROKEN`, `MAINT` или `EMPED`. Изменения приходят через `set_machine_stat()` и новый сигнал `COMSIG_MACHINERY_SET_MACHINE_STAT`.
- Сетевой модуль APC питается от собственного питания APC. Его отключают главный рубильник, перерезанные силовые провода, сбой питания (`failure_timer`) и отсутствие внешнего питания и заряда ячейки. Закрытые каналы оборудования и парковка APC модуль не выключают.
- APC без платы, сломанный и после EMP неисправен. EMP выставляет APC флаг `EMPED` до штатного сброса через 60 секунд.

## P4 · пилот телеметрии `atmos.telemetry` (Shadow)

### Транспорт: быстрые провода

`PacketTransportOptions.MaxCableHopsPerTick` (1..64, по умолчанию 1) задаёт, сколько кабельных переходов пакет проходит за один тик транспорта. По проводу не тратится эфирное время, поэтому подряд идущие кабельные переходы проходятся в пределах тика. Радиопереход по-прежнему ждёт следующего тика и своего эфирного времени. Кабельным считается переход, у которого оба конца разрешают транзит, а провод не дороже радио. Игровой runtime Host использует 64 (с P8; было 16), бенчмарки — прежнее значение 1. `AdvanceInteractiveOnSubmit` (по умолчанию выключено, в игровом runtime включено): интерактивный пакет, принятый после прохода текущего тика, сразу делает первый переход и провода за ним в этом же тике, вместо ожидания следующего прохода до 100 мс. Учёт эфира тот же, фоновый трафик идёт по расписанию тиков. Обработка одного пакета вынесена в `VisitPacket` и общая для прохода тика и быстрого пути. Квант транспорта — 100 мс, поэтому проводная магистраль занимает один квант вместо кванта на каждый переход.

### Команда снимка

`atmos.telemetry/sample`: аргументы — `atmos.sample_request` 1 с необязательным полем `{reason: subscribe | refresh}`, результат — полный `atmos.sample` 1. Запрос и результат идут по сети как обычная команда P2.2. Неполный ответ провайдера даёт `applied` с `result=failed` и до инициатора не доходит.

### Сервисный канал BlueMoon

`/datum/netdm_service_lane` в `SSnetdm_observe` хранит желаемое состояние endpoint и отправляет в Host только недостающее. Желаемое состояние — это присоединение к узлу, сервисы и подписки.

- ID endpoint `e<n>` живут весь раунд. Подтверждённое Host состояние живёт одну сессию и после нового snapshot восстанавливается само.
- Если узел ушёл из сети или получил новый ID, endpoint присоединяется заново с большей generation.
- У каждого endpoint в полёте не больше одного запроса: присоединение, регистрация и подписка идут по порядку. Всего в полёте не больше 16 запросов канала, у них собственный срок ответа 20 с реального времени. При 4 запросах на Box Station девять датчиков, отчитавшихся в одном тике, ждали в очереди DM лишние 2–3 срабатывания (p95 550 мс). Пакетная публикация одним запросом — следующий шаг для нагрузочной проверки.
- Публикации экземпляра сворачиваются до последнего значения.
- Отказ в регистрации или подписке пишется в лог и не повторяется. Подписка на ещё не зарегистрированный экземпляр повторяется с паузой от 5 с, она удваивается до 60 с.
- Host снимает все подписки на экземпляры поставщика вместе с его endpoint (`provider_gone`) и сам не переносит их на нового поставщика. Подписчик об этом сообщения не получает. Поэтому канал держит индекс «экземпляр → подписчики» и, когда поставщик уходит (новый узел, новая generation, удаление устройства) или успешно регистрирует экземпляр, подписывает их заново сразу, без паузы повтора. Действующая подписка отвечает `duplicate`. Ответ на подписку, отправленную до смены поставщика, не принимается: подписка повторяется. Это работает для поставщиков и подписчиков одного DM-процесса. Подписчику в другом процессе нужно уведомление Host, его пока нет.
- Inbox опрашивается каждое срабатывание в течение 3 с после публикации, команды или полученного элемента, в остальное время — раз в секунду. Элементы обрабатывает allowlist-диспетчер P2 с ACK пачками до 64.
- Порядок в срабатывании: ACK, опрос inbox, присоединение и подписки, публикации, команды, запросы `delivery_status`. Опрос идёт раньше новой работы: доставленное уже ждёт в inbox. Запросы статуса — диагностика, они не задерживают опрос.
- Для диагностики канал считает наибольшую паузу между опросами и самый долгий ответ Host с типом запроса (`poll_gap`, `reply_max` в состоянии канала). Долгий ответ указывает на Host, долгая пауза при коротких ответах — на сам канал.

### Пилот в режиме Shadow

Датчик газа `air_sensor` — экземпляр `atmos.<частота>.<id_tag>`. Это та же пара, что связывает датчик с консолью по радио. Каждый радиоотчёт датчика публикуется как `atmos.sample` с `sampleTick`, равным номеру тика отчёта. Консоль `atmos_control` подписывается (`latest_value`, проекция `full`) на экземпляры датчиков из своего списка и после подписки один раз за сессию запрашивает снимок командой.

Доставки только записываются. Экран консоли по-прежнему показывает радиоотчёт. Каждый отчёт через 5 с сравнивается:

- какие консоли получили его по радио, а какие по сети;
- задержка от отчёта датчика до обработки в консоли, сквозная, с учётом очереди DM, Host, транспорта и опроса inbox;
- для консоли, которую радио достигло, а сеть нет, — причина из `delivery_status` по `messageId` (`invalid_route`, `no_route`, `expired`, `newer_value`) или `not_subscribed`. Host фиксирует получателей при приёме публикации. Если доставки консоли нет, а её подписка отправлена позже публикации, причина — `subscribed_later`. Без такого объяснения остаются `not_recipient` и `no_recipients`, это дефект. Только `invalid_route` и `no_route` кэшируются на 30 с, остальные причины запрашиваются для каждого отчёта.

Сводка видна в MC-панели: число сравнений, совпадений, только-радио, только-netDM, p50/p95/max и причины. `SSnetdm_observe` не фоновая подсистема. Экспорт карты берёт не больше 15 % тика за срабатывание. Host показывает счётчики транспорта, тиков и сервисов на локальном `GET /api/game/status`. Радио доставляет отчёт всем консолям частоты независимо от Z, питания и исправности, поэтому разница с netDM — ожидаемое отличие новой модели. Сравнение показывает её с причинами.

## P5 · сервисы исследований

### Реестр исследований в Host

У каждого физического R&D-сервера своё хранилище в реестре Host: знания (открытые узлы, бусты, ревизия) и кошелёк. Кошельки ведутся в милли-очках (`long`). Реестр — единственный писатель исследований в Host, все операции идут под одной блокировкой.

- **Журнал.** На раунд один файл `research-<roundEpoch>.journal` в `NetDM:ResearchDirectory`. Формат: заголовок `NDMRJ001`, затем записи `[длина int32][crc32][JSON]` до 64 КиБ. Изменение сначала дописывается в журнал и сбрасывается на устройство (`Flush(true)`), только потом применяется в памяти и подтверждается. При открытии всё до оборванного или повреждённого хвоста воспроизводится. Хвост отрезается только после того, как реестр принял воспроизведённые записи: журнал, от которого сборка отказалась (другой раунд, более новый формат, неизвестная запись), не изменяется ни на байт. Журнал хранит эффекты (списано, открыто, ревизия, ответ), поэтому для воспроизведения каталог не нужен.
- **Версия формата.** Вторая запись журнала — `format {version}`, сейчас версия 2. Версия описывает смысл записей, а не контейнер `NDMRJ001`. Сборка не открывает журнал с версией выше своей или с неизвестным видом записи: файл не изменяется, реестр остаётся закрытым, операции отвечают `research_unavailable`. Так откат Host на более старую сборку внутри раунда даёт явный отказ, а не чтение записей с другим смыслом. Журнал версии 1 (без записи `format`) принимается один раз: при открытии в него дописывается `format {2}`, состояние сохраняется. Новый вид записи или новый смысл существующей повышают версию. Изменение самого контейнера (предел записи, контрольная сумма) меняет заголовок: иначе старая сборка приняла бы непонятную запись за оборванный хвост и отрезала её.
- **Готовность хранилища (§17.4).** Состояние видно в `research` готовности и в `storage` статуса:
  - `ready` — журнал раунда открыт и последняя запись дошла до устройства;
  - `faulted` — запись не удалась. Её исход на диске неизвестен, поэтому реестр больше ничего не пишет и не применяет: операции отвечают `journal_failed`, чтение состояния работает;
  - `unavailable` — журнал не открывается (нет доступа к пути, ошибка чтения);
  - `refused` — файл не является журналом этого раунда известного формата. Он не изменяется, повторы не помогут;
  - `closed` — ни одна сессия ещё не назвала раунд.
- **Проверка записи при открытии.** Чтение существующего журнала ничего не говорит о следующей записи (том переполнен или доступен только на чтение, файл заблокирован). Поэтому Host, открыв существующий журнал, дописывает в него запись `format {version}` текущей версии. Она воспроизводится без последствий и повторяется по одному разу на каждое открытие. Новый журнал только что записан и отдельной проверки не требует.
- **Восстановление без перезапуска Host.** Из `faulted` и `unavailable` Host выходит сам: закрывает файл, заново воспроизводит журнал с диска и проверяет запись. Воспроизведение решает и исход неудавшейся записи: оборванная отрезается, целая принимается. Реестр в памяти при этом не используется.
  - Попытки идут по реальному времени: сразу после сбоя, затем не чаще чем через 1, 2, 4 … 30 с. Интервал сбрасывается после минуты без попыток. Каждый `hello` своего раунда даёт попытку вне очереди.
  - Пока попытка не удалась, готовность остаётся ложной: открытие, после которого проверка записи не прошла, оставляет состояние `faulted`.
  - DM повторяет отклонённые операции под теми же ID и после восстановления заново загружает каталог.
  - Сбой обнаруживается первой неудавшейся записью. Фоновой пробы диска нет.
- **Запись без буфера.** Файл журнала открыт без внутреннего буфера потока: запись, которую отвергло устройство, не остаётся в памяти и не попадает в файл при закрытии. Воспроизведение читает через собственный буфер и не запрашивает байты за концом файла.
- **Раунд.** Реестр открывается по `roundEpoch` из `hello`. Сессии и пересинхронизации того же раунда, а также перезапуск Host, продолжают тот же журнал. Журнал другого раунда не открывается.
- **Каталог** — статическое содержимое из DM: узлы, предпосылки, design ID, стоимости в целых очках, флаги starting/hidden/experimental. Hash — SHA-256 канонической формы. Первый каталог раунда записывается в журнал. Потом принимается только тот же hash, другой блокирует запись (`catalog_mismatch`). После перезапуска Host DM загружает каталог заново. Предпосылки должны существовать. ID узлов — `[A-Za-z0-9_.-]`, до 64 символов. Design ID — печатный текст до 64 символов: в данных есть `"power control"`.
- **Операции:**
  - регистрация и уничтожение хранилища. При уничтожении очки уходят в `lost`, а не переносятся.
  - доход за интервал, однократно для `{storage, generation, interval}`.
  - награда и штраф, однократно на раунд для `{sourceEvent, kind}`. Штраф не опускает кошелёк ниже нуля.
  - импорт знаний без оплаты и наград, однократно для источника.
  - буст по доказательству, однократно.
  - покупка узла.
- **Покупка** атомарна. Проверяются: хранилище живо, каталог установлен, узел известен и ещё не открыт, при необходимости ожидаемая ревизия, скрытый узел раскрыт, предпосылки есть. Цена — стоимость каталога минус лучший буст, не ниже нуля. Ошибку legacy `get_price` реестр не повторяет. Цена должна совпасть с котировкой из запроса, иначе `quote_changed`, и ничего не списывается. Затем проверяется баланс. Ответ любой покупки, включая отказ, записывается под её operation ID: повтор, в том числе после перезапуска Host, возвращает записанный ответ.
- **Эффект покупки (outbox, §13.5).** Покупка с исходом `researched` должна миру: узел в legacy-сети, которую читают станки, bounty и запись в журнале исследований. Это обязательство порождает сама запись покупки, отдельной записи создания нет: состояния «покупка зафиксирована, обязательства нет» не существует.
  - ID эффекта — `<storage>/<operationId>`, вид — `researched`. Отказ, повтор покупки, импорт, синхронизация и диск эффектов не создают.
  - Эффект ждёт, пока DM не сообщит исход. Исход фиксирует запись `effect {id: result}`. Эффект закрывается один раз: повторный или неизвестный ID ничего не меняет, первый исход сохраняется.
  - Ожидающие эффекты переживают перезапуск Host под теми же ID и выдаются снова, пока исход не записан. Уничтожение хранилища обязательство не снимает: исход определяет мир.
  - Покупки журнала версии 1, записанные до `format {2}`, эффектов не создают: их последствия применил прежний протокол.
- **Инвариант** по каждому типу очков: начислено = доступно + потрачено (покупки и штрафы) + потеряно. `/api/research/status` показывает хранилища, суммы, `balanced`, число воспроизведённых записей и отрезанных байт, `journalFormat`, `effects {pending, settled}` с числом закрытых эффектов по исходам, состояние хранилища `storage` и число восстановлений `recoveries`. У каждого хранилища есть `knowledge` — номер последней записи его журнала знаний.

### Управляющие операции DM

`research_catalog {catalog, chunk, chunks, pointTypes, nodes}` — по частям, в порядке. Последняя часть проверяет каталог целиком и сообщает первый дефект. Остальные операции:

- `research_storage {storage, generation, domain, action: register|destroy}`;
- `research_income {interval, grants: [{storage, generation, points}]}` — пакет под один сброс журнала;
- `research_grant` и `research_debit` `{storage, generation, source, kind, points}`;
- `research_import {storage, generation, source, nodes}`;
- `research_boost {storage, generation, node, evidence, discount}`;
- `research_state {storage?}`;
- `research_effects {settle?: [{id, result}], max?}` — outbox покупок. Сначала закрываются перечисленные эффекты (до 64 за запрос, `result` — код `[A-Za-z0-9_.-]`), затем возвращаются самые старые ожидающие: `{settled, pending, effects: [{id, kind, storage, op, node, price, revision}]}`, до 16 за ответ. Чтение ничего не закрывает. Некорректный отчёт отклоняется целиком (`invalid_request`).
- `research_knowledge {storage, since, max?}` — журнал знаний самого сервера: `{storage, revision, upto, more, nodes}`, узлы после записи `since` по порядку записей, до 64 записей за ответ. Чтение ничего не меняет. Неизвестное или уничтоженное хранилище — `storage_unavailable`. Это состояние сервера для мира, в котором он стоит, а не сообщение между устройствами: оно не ждёт обратного пути ответа по игровой сети (см. «Проекция знаний» в P6).

Поля лежат в `payload`. Милли-очки передаются текстом: числа DM 32-битные. В ответах Host 64-битные целые тоже приходят текстом. Операции доступны сразу после `hello`, опубликованная топология им не нужна: хранилище, доход и награды принадлежат самому серверу.

### Сервис `research.server`

Экземпляр `research.<storage>` регистрирует endpoint сервера. Схема сервиса — `research.status`. Команды сервиса выполняет Host: в `ServiceRuntime` тип объявлен как `HostProvidedTypes`. Команда проходит смоделированный маршрут до узла сервера, Host забирает её через `TakeHostCommands` и отвечает через `Acknowledge`. Ответ возвращается отдельным плечом результата.

- `research`: аргументы `research.request` 1 `{node, quote, revision?}` в целых очках, результат `research.result` 1 `{outcome, node, revision, price, available}`. Исходы: `researched`, `already_researched`, `prerequisites_missing`, `quote_changed`, `insufficient_points`, `unknown_node`, `stale_revision`, `storage_unavailable`, `catalog_unavailable`. Ключ идемпотентности команды и есть operation ID реестра.
- `status`: результат `research.status` 1 `{state, revision, available, unlocked, catalog}`.

Сервер вне досягаемости покупку не получает: нет маршрута — нет покупки. Обесточенный сервер теряет связи (P3.5).

### Пилот BlueMoon в режиме Shadow

R&D-сервер и R&D-консоль становятся узлами netDM. Сервер регистрирует хранилище `srv-<endpoint>` и сервис. Первый сервер legacy-сети становится её казной. Казна получает текущие очки сети (`seed`, `migration`), её открытые узлы (импорт) и бусты, затем каждое изменение через примитивы techweb:

- `commit_income` — доход интервала;
- `add_point_list(income = FALSE)` — награда;
- `remove_point_list` и `modify_point_list` — фактическое изменение в обе стороны;
- принудительные открытия — импорт;
- `boost_with_path` — буст.

Хуки лежат в `code/modules/research/techweb/netdm_research_hooks.dm`: этот файл компилируется после legacy-определений. Покупка на консоли, которую совершила legacy-сеть, уходит командой `research` к казне по сети. Котировка — фактически списанная legacy-сетью сумма. Покупка отправляется только после того, как Host подтвердил все предшествующие события зеркала. Ответ сравнивается с legacy, несовпадение получает причину. После несовпадения казна выравнивается импортом узла и списанием цены, и одна причина не размножается. Раз в 15 с, пока нет неподтверждённых событий и покупок в пути, баланс и число узлов казны сверяются с сетью. Раздельные кошельки серверов из дизайна здесь не сравниваются. На карте Runtime Station под Observe рядом с R&D-консолью ставится R&D-сервер: на этой карте его нет.

### Авторитетный режим исследований (AuthoritativeCanary)

`NETDM_RESEARCH_MODE=authoritative` при Observe включает переход, как только зеркало синхронизировано. Тест может вызвать `authorize()` сам. По умолчанию — Shadow. Обратного перехода в раунде нет. Миграция по §13.11:

- казна сети уже держит её пул;
- остальные серверы сети получают её знания и бусты (`migration-<storage>`), но не копию баланса;
- `next_income` один раз переходит в казну;
- консоли привязываются к ближайшему серверу своей сети.

После перехода для сети с сервером действуют правила дизайна:

- **Доход.** Каждый сервер получает свой доход в свой кошелёк. Расчёт — legacy-формула `mine()`, коэффициент убывающей отдачи считается по работающим серверам домена, то есть сети сервера. Разрез сети число не меняет, его меняет только перепривязка мультитулом. Legacy-пассивный доход `SSresearch` для такой сети не начисляется.
- **Прочие начисления, штрафы и бусты** (`add_point_list`, `remove_point_list`, `modify_point_list`, `boost_with_path`) становятся событиями реестра для координатора сети (казны). Legacy-баланс `research_points` — только справочная проекция: раз в 10 с туда пишется сумма кошельков серверов сети. Сами примитивы его не меняют и не тратят.
- **Покупка.** Консоль покупает на сервере, к которому привязана, командой `research` по сети. Котировка — цена реестра: экспортированная стоимость узла минус лучший буст этого сервера. Ответ приходит позже. При `researched` узел открывается в legacy-сети, станки и фабрикаторы читают её как объединение знаний серверов. Затем `on_node_researched` и сигнал синхронизации станков, журнал исследований, одна выплата bounty. Остальные исходы консоль сообщает текстом. Повтор после потерянного ответа безопасен: реестр вернёт записанный ответ или `already_researched`.
- **Bounty** платится один раз за покупку. Принудительные открытия, диски, синхронизация станков и импорт bounty не платят.
- **Эффекты покупки в мире.** Ответ сервера, дошедший до консоли по сети, сообщает игроку исход. Последствия покупки в мире (узел в legacy-сети, bounty, журнал исследований) — это эффект реестра. DM применяет его один раз за раунд по ID эффекта: когда пришёл ответ `researched`, либо из outbox, если ответ потерян (нет обратного маршрута, истёк срок, сброс сессии, перезапуск Host). Outbox опрашивается сразу после покупки без ответа и при неотправленных отчётах, иначе раз в 5 с, одним запросом в полёте. Исходы: `paid` и `unpaid` (применён, с bounty или без), `shadow` (покупку уже применила legacy-сеть: режим Shadow, ключи `rc-`), `void` (в мире не осталось сети, к которой её применить), `failed` (применение завершилось рантайм-ошибкой DM). Эффект помечается закрытым до применения: после рантайм-ошибки он не применяется повторно, bounty не платится второй раз, а сбой виден в `effects.settled.failed`. Эффект, который Host выдал повторно, не применяется, а его исход отправляется снова. До этого изменения потерянный ответ оставлял списанные очки без bounty и без записи журнала: повтор получал `already_researched`.
- **`get_price`** для такой сети не меняет общий узел: стоимость берётся из экспортированного каталога за вычетом буста сети.
- **Привязка консоли.** По умолчанию — ближайший сервер сети. С 13.11.2026 «ближайший» определяет сеть: консоль спрашивает у АПЦ своей зоны, до каких серверов `research.server` тот дотягивается (`network.query/services`), и берёт сервер своей исследовательской сети с наименьшим числом переходов. Сервер, до которого сеть не дотягивается, не предлагается, как бы близко он ни стоял. Если спросить некого (в зоне нет АПЦ) или ответа нет, выбор идёт по расстоянию на карте, как раньше. Ответ применяется, только пока консоли всё ещё нужен сервер: привязка, сделанная тем временем мультитулом, остаётся. Мультитул, коснувшийся сервера и затем консоли той же сети, переносит адрес сервера (§13.3). Привязка подтверждается только ответом `status` по сети. Обновление — раз в 10 с. Окно консоли показывает кошелёк привязанного сервера, его доход в секунду, состояние и возраст данных, цены реестра и доступность по этому кошельку. Если сервер уничтожен, консоль переходит к другому серверу сети. Кошелёк уничтоженного сервера потерян.

`scripts/test-bluemoon-unit.ps1 -ResearchMode authoritative` и `scripts/start-bluemoon-stand.ps1 -ResearchMode authoritative` включают режим на прогоне и на стенде.

## P6 · синхронизация, переводы, диски

### Реестр

- **Журнал знаний.** У каждого хранилища есть журнал знаний: каждое открытие узла и каждое повышение буста получает следующий номер записи. `Delta(storage, since, max)` отдаёт записи после `since` пачкой, с `upto` и признаком `more`. Для каждой пары «получатель ← источник» хранится водяной знак — последний уже перенесённый номер.
- **`Replicate`** принимает записи от пира того же домена. Неизвестные узлы добавляются, бусты объединяются по максимуму скидки, водяной знак растёт. Повтор пачки и цикл A→B→C→A ничего не меняют. Очки, доход и заряды не переносятся. Пир другого домена — `forbidden`, узел вне каталога — `unknown_node`.
- **Переводы.**
  - `Reserve` переносит очки источника в escrow. Идемпотентно по ID перевода, другое содержимое — `conflict`. Нужны тот же домен и достаточный остаток.
  - `CommitTransfer` переносит escrow на счёт получателя. Принимается только названный получатель живой генерации и до срока. Повтор возвращает то же состояние.
  - `CancelTransfer` и `ExpireTransfers` возвращают escrow живому источнику, а escrow уничтоженного источника становится `lost`.
  - Срок по умолчанию — 60 с реального времени Host, он хранится в журнале. Зарезервированный перевод переживает перезапуск Host.
  - Инвариант: начислено = доступно + escrow + потрачено + потеряно.
- **Диски.**
  - `Backup` записывает знания хранилища в манифест диска (узлы, бусты, hash каталога) одной записью. Очков в манифесте нет, такое же содержимое — дубликат.
  - `Restore` добавляет недостающие знания, новые знания хранилища не откатывает. Стоимость, награды, доход и очки не начисляются. Одна версия диска применяется к хранилищу один раз. Диск другого каталога отклоняется.

### Сетевые команды `research.server`

- **Общий счёт сети.** Отвечая на `research`, Host передаёт реестру плательщиков. Это живые хранилища того же домена, узлы серверов которых достижимы от узла сервера покупки одним поиском `ReachAll`; порядок — по стоимости маршрута, затем по ID. Покупатель платит первым, остаток — плательщики по порядку, всё одной записью журнала с полем `Payers`. Цена остаётся ценой покупателя, по его знаниям и бустам, и знания тоже открываются покупателю. Записи без `Payers` (журналы до этого изменения) воспроизводятся как оплата покупателем. `available` в ответах `research` и `status` теперь равен сумме общего счёта.

- `sync {since}` → `research.sync_delta {nodes, boosts, upto, more, revision}`. Узлы передаются текстом `a,b,c`, бусты основного типа очков — `node=amount;…`. Пачка — до 50 записей.
- `transfer_out {transfer, to, amount}` выполняется на источнике и резервирует. `transfer_in {transfer, from, amount}` выполняется на получателе: это авторизация, которую источник отправляет по сети, и она фиксирует перевод. Ответ — `research.transfer_state {transfer, state, reason?, amount, available}`. Авторизация с другим источником или суммой — `refused`/`mismatch`.
- `backup {disk}` и `restore {disk}` → `research.disk_state {disk, state: written|restored|unchanged|refused, nodes, reason?}`.
- Текстовое поле схемы теперь до 4096 символов. Весь payload по-прежнему ограничен 8 КиБ.
- Управляющая операция DM `research_replicate {storage, generation, peer, upto, nodes, boosts}` фиксирует знания, которые сервер получил по сети, и возвращает новый водяной знак. Состояние Host показывает escrow и последние 32 перевода.

### BlueMoon

Всё ниже работает в авторитетном режиме.

- **Домен** хранилища — сеть сервера: `station` для станционной, `web-<hash>` для остальных. Хранилище регистрируется, когда сеть сервера известна.
- **Синхронизация.** Каждый сервер раз в 15 с запрашивает журнал каждого пира своего домена командой `sync` по сети. Ответ приходит на узел сервера и фиксируется через `research_replicate`. Если записей больше, следующий запрос уходит сразу.
- **Общий счёт сети (вместо ручного перевода, 12.11.2026).** Консоль тратит очки всех серверов своего домена, до которых сервер консоли дотягивается по сети. Глагола «Собрать очки на сервер» больше нет, и BlueMoon переводов не вызывает. Команды `transfer_out` и `transfer_in` реестр по-прежнему поддерживает.
- **Диски.** Кнопки диска консоли «Download to disk» и «Upload disk» (`loadTech` и `uploadDisk`) работают через привязанный сервер: `backup` и `restore`. Диск получает ID реестра при первой записи. Диск без ID (лут, legacy) идёт по старому пути. После записи на диск остаётся legacy-копия знаний сети для машин, которые читают techweb.
- **Проекция знаний (13.11.2026).** Legacy-сеть, которую читают станки, держит объединение знаний своих серверов. О покупке ей сообщает эффект покупки. Всё остальное, что научило сервер (загруженный диск, пир, импорт), DM читает из журнала знаний сервера операцией `research_knowledge`.
  - Раз в 10 с состояние реестра называет `knowledge` каждого хранилища. Если номер больше того, что уже перенесено, DM читает журнал страницами по 64 записи, одним запросом в полёте, и открывает недостающие узлы в сети сервера. Bounty, очки и запись журнала исследований при этом не появляются.
  - Ответ консоли на `restore` остаётся сообщением игроку. Если он потерян, знания всё равно доходят до сети. Раньше в этом случае сервер знал узлы, а станки их не видели.
  - Номер перенесённой записи DM хранит в памяти и не сбрасывает при новой сессии: журнал знаний после перезапуска Host воспроизводится с теми же номерами. Если реестр начался заново и его номер меньше, журнал читается с начала. Повторное чтение безвредно: открытый узел не открывается второй раз.
  - Сеть без сервера-координатора ждёт следующего сервера. Знания уничтоженного сервера, которые не успели дойти, уходят вместе с ним.
  - Host без этой операции отвечает `Unknown operation.`: DM до конца сессии её не повторяет, и сеть следует только за ответами, как раньше.
  - Открытый вопрос. При ответе `restored` DM по-прежнему копирует legacy-копию диска, а в ней знания всей сети на момент записи, а не одного сервера. При переносе диска в другую сеть legacy-сеть может получить больше, чем записал реестр. Выравнивание по реестру меняет игровое поведение и ждёт решения.
- **Bounty** в авторитетном режиме не платится за принудительные открытия ни в одной сети, включая сам диск.

### Сроки ответа и диагностика bridge

`SSnetdm_observe` ждёт ответа на запрос 20 секунд реального времени, после чего начинает новую сессию. Срок считается по `REALTIMEOFDAY`, а не по `world.time`: на Windows-стенде машина периодически останавливала все процессы на 5–8 с, после чего тики догоняют время быстрее, чем приходят ответы. Host закрывает молчащего владельца через 30 с.

Рабочий поток Win32 bridge ждёт событие, которое взводит `netdm_send`, вместо `sleep_for`: отправка не ждёт тайм-аута простоя. `netdm_status` дополнительно сообщает `iterations`, `framesOut`, `framesIn`, `bytesIn`, `phase` (0 простой, 1 запись, 2 чтение, 3 подключение), `sinceIterationMs` и `maxGapMs`. `NETDM_BRIDGE_WAIT=std` возвращает прежнее ожидание для сравнения. При `NETDM_BRIDGE_TRACE=1` подсистема пишет эти счётчики в лог раз в две минуты, а таймаут ответа всегда пишет их вместе с ожидаемым запросом и числом отброшенных адаптером сообщений.

## P7 · мессенджер `pda.messenger` (Shadow)

### Схемы и команда

- `pda.message` v1: `{id, text, sender, automated?, photo?}`. ID — до 64 символов, текст — до 4000, имя отправителя — до 128, весь payload — до 8 КиБ. Передаются только скаляры: ID сообщения, санитизированный текст, отображаемое имя и флаги. Ссылок DM, `REF`, путей и base64 нет.
- `pda.receipt` v1: `{id, state, reason?}`, где `state` — `shown`, `recorded`, `duplicate`, `blocked` или `disabled`.
- Команда `pda.messenger/deliver` принимает `pda.message` и отвечает `pda.receipt`. Она адресная: инициатор — узел КПК отправителя, исполнитель — экземпляр `pda.<endpoint>` получателя. Ключ идемпотентности — `<ID сообщения>.<endpoint получателя>`, поэтому повтор той же доставки новой операции не создаёт.
- Квитанция возвращается к отправителю отдельной сетевой ногой результата. `TransportDelivered` команды не означает показ: показан ли текст, говорит только состояние квитанции.

### BlueMoon

- **Узел.** Каждый компьютер с мессенджером — мобильный радиоузел с экземпляром `pda.<endpoint>`. Узел регистрируется при записи программы на жёсткий диск (так программы ставят КПК и планшеты, `on_install` при этом не вызывается), при прямой записи (`on_install`) и при запуске программы. Удаление программы снимает записи пилота, а узел уходит вместе с компьютером.
- **Зеркалирование.** Перед легаси-отправкой создаётся запись с ID сообщения. Сигнал `datum/signal/subspace/messaging` получает `netdm_id`, и копии сигнала его сохраняют. После легаси-вызова каждому получателю уходит `deliver`. Зеркалируется и неудачная легаси-отправка, если сигнал уже построен («Server is not responding»): так видно, что сеть доставила бы и без message server.
- **Исключения совместимости** считаются, но не зеркалируются: фото (в V1 нет lifecycle вложений), рассылка всем, больше 8 получателей, rigged и автоматические сообщения, текст длиннее 4000 символов.
- **Получатель в Shadow** ничего не показывает. Он запоминает ID сообщения и отвечает `recorded`, повтор получает `duplicate`. Окно дедупликации — 2048 ключей, при переполнении обрезается до 1024.
- **Сравнение** через 10 с после отправки по каждой паре «сообщение — получатель»: `matched`, `legacy_only`, `netdm_only` или ни один путь. Для `legacy_only` причина — состояние квитанции или исход команды из Host (`query_command`). Для `netdm_only` причина — `legacy_server` (легаси не нашёл сервер) или `legacy_missed`. Одновременно сравнивается до 256 сообщений, при переполнении старейшее сравнивается досрочно.
- **Метрики.** `arrival` — от легаси-отправки до приёма команды на узле получателя. `receipt` — до возврата квитанции отправителю.

### Авторитетный режим: доставка через message server

**Схемы и команды.**

- `pda.message` получил необязательное поле `from` — экземпляр мессенджера отправителя. По нему получатель находит чат для ответа.
- `pda.relay` v1: `{id, text, sender, to}`. `to` — от 1 до 8 экземпляров `pda.*` через запятую, до 1024 символов.
- `pda.relay_state` v1: `{id, state, recipients?, reason?}`, где `state` — `queued`, `offline` или `refused`.
- `pda.delivery` v1: `{id, recipient, state, reason?}`, где `state` — `delivered`, `duplicate`, `blocked`, `disabled` или `unreachable`.
- Команды: `pda.server/relay` (`pda.relay` → `pda.relay_state`) и `pda.messenger/status` (`pda.delivery` → `pda.receipt`).
- Host игры разрешает одной конечной точке 32 одновременные операции вместо 8: сервер рассылает всем получателям из одной точки.
- Сервисный канал DM: `invoke` принимает срок жизни команды в тиках Host (по умолчанию 50, не больше 900). Команда, узел которой отключился до отправки, получает ответ `detached`, а не теряется молча. Команду, которую bridge не принял, канал возвращает в начало очереди.

**Поток.**

1. **Отправитель.** Легаси-отправка строит сигнал как раньше. Подходящее сообщение (не исключение совместимости) вместо телекомма уходит командой `relay` на сервер с ключом идемпотентности, равным ID сообщения. КПК шлёт на зарегистрированный сервер своего уровня Z, иначе на первый известный. Включён ли сервер, КПК узнаёт только из ответа. Нет сервера или переполнен канал — легаси пишет «Server is not responding». Синтетики и отладочный обход, как и раньше, доставляют напрямую.
2. **Сервер.** Выключенный, обесточенный, сломанный или под EMP сервер отказывает с причиной `offline`. Иначе он проверяет отправителя по `producer` команды и получателей, пишет одну запись в журнал монитора сообщений, как легаси, и отвечает `queued`. Доставки он ставит в свою очередь до 256 записей. Повтор `relay` с тем же ID журнал не пишет и не рассылает заново. Переполненная очередь даёт `refused` с причиной `busy`.
3. **Доставка.** Сервер шлёт `deliver` каждому получателю со своего узла, с ключом `<ID>.<endpoint>` и сроком 300 тиков (30 с): получатель, ненадолго вышедший из зоны, ещё получит сообщение. Отказ Host `busy` возвращает доставку в очередь.
4. **Получатель** показывает сообщение один раз через легаси-представление (чат, «Ответ», «Блок», рингтон) и отвечает `shown`. Повтор даёт `duplicate`, заблокированный отправитель — `blocked`, выключенный приём — `disabled`. Отправителя, которого нет в списке контактов, получатель добавляет туда, как легаси-поиск по `GLOB.PDAs`.
5. **Статус.** Сервер переводит квитанцию в статус и сообщает его отправителю командой `status`. Если квитанции нет, когда доставка уже не может прийти (срок доставки плюс 5 с), сервер спрашивает Host о своей операции и сообщает `unreachable` с причиной.
6. **Отправитель видит:** при `queued` — ничего нового, легаси уже написал «PDA message sent». При отказе сервера или без ответа 10 с реального времени — «ERROR: Server is not responding.». При `unreachable` и `disabled` — ошибку с именем получателя, при `blocked` — легаси-фразу о блокировке. `delivered` проходит молча.

**Чего сеть не утверждает.** Об отказе доставки отправитель узнаёт только от сервера, а об отказе сервера — только по своему таймауту. После сброса сессии Host операции в пути не повторяются: такие сообщения получают «нет ответа», хотя сервер мог их принять.

**Режим** включает `NETDM_MESSENGER_MODE=authoritative` (у скриптов стенда — `-MessengerMode`) или `set_authoritative()`. В Shadow сервер узлом сети не становится.

## P8 · радиоречь (Shadow)

### Аналитическое вещание в Core

`SharedMediumNetwork.ReachAll(snapshot, sources, targets)` одним поиском Дейкстры находит кратчайшие маршруты от любого из источников до каждой цели. Так считается раздача вещания (§9.5) вместо отдельного маршрута на каждого слушателя. Источник передаёт, даже если он конечная точка. Любой другой узел пересылает только с `CanForward`: конечную точку можно достичь, но через неё не пройти. Поиск останавливается, когда все цели найдены.

Для каждой цели `BroadcastReach` даёт стоимость, число звеньев и радиозвеньев, последний узел перед целью и тики так, как их пройдёт транспорт. Звено начинает тик, провода за ним идут в том же тике до 16, следующее радиозвено ждёт нового тика. Конкуренция за эфир не учитывается. Перегрузка с начальным состоянием источника продолжает маршрут через шлюз: звенья, тики и текущий провод переходят дальше.

### Операция `radio_reach`

Управляющая операция DM (`bridge.radio`): `{source, receivers[], broadcasters[], targets[]}` — ID узлов, до 64 приёмников и вещателей, до 1024 целей. Host ничего не передаёт и не меняет. Он считает три участка одной передачи:
1. от радио говорящего до ближайшего приёмника;
2. от приёмника до вещателей;
3. от вещателей до каждого слушателя.

Приёмник и вещатель продолжают ту же передачу как шлюзы, своего тика на обработку не добавляют.

Ответ: `{reason, receiver, uplinkHops, uplinkRadioHops, broadcasters, ticks[], hops[], transmissions, reached}`. `ticks[i] = -1` значит, что цель недостижима. `reason` (`no_source`, `no_uplink`, `no_chain`) объясняет, почему не достигнут никто. `transmissions` — число различных последних узлов перед слушателями по радио, то есть сколько радиоячеек заняла бы одна передача.

### BlueMoon

- **Узлы.** Каждое радио `/obj/item/radio` — узел сети: интерком закреплённый (провод к APC своей зоны), остальные мобильные (радио). Приёмники, вещатели и all-in-one телекомма — закреплённые узлы.
- **Выборка.** Вокальный сигнал получает ID, копии через телекомм его сохраняют. Каждая легаси-рассылка подпространства добавляет к записи радио, которые её получили, по тем же правилам, что легаси: `can_receive` на уровнях копии и изоляция учебных зон. Приёмники берутся включённые, запитанные и слушающие частоту. Пилот берёт до 4 передач в секунду и держит до 16 записей. Остальное считается невыбранным, запись без вопроса дольше 5 с выбрасывается.
- **Вопрос и сравнение.** После всех рассылок сообщения, на следующем тике, DM спрашивает Host, не больше 4 вопросов одновременно. Каждый слушатель либо сопоставлен с оценкой задержки (тики × 100 мс), либо объяснён (`no_uplink`, `no_chain`, `no_downlink`, `source_unregistered`). Радио, ещё не ставшее узлом, считается `unregistered`.
- **Исключения** считаются, но не сравниваются: обычная резервная передача не-гарнитур, суперпространство независимых радио, источник-машина и синдикатские добавки известных каналов.

### Авторитетный режим: аплинк по сети

Пользователь выбрал модель «аплинк по сети». Говорящий должен дотянуться по сети до приёмника телекомма. Раздача остаётся подпространственной: вещатель озвучивает все радио своего уровня, как раньше.

- **Схемы.** `radio.uplink` v1 `{id, frequency}` и `radio.uplink_state` v1 `{id, state}`, где `state` — `relayed`, `ignored`, `duplicate`, `late` или `expired`. Команда `radio.receiver/uplink`.
- **Контекст речи.** Сама речь (говорящий, язык, спаны, сжатие) остаётся в DM: вокальный сигнал лежит в таблице контекстов до 5 с, не больше 256 записей. По сети идут только ID контекста и частота (§8.4).
- **Отправитель.** Вместо `send_to_receivers()` радио отправляет `uplink` каждому зарегистрированному приёмнику, который слушает его частоту. Включён ли приёмник, решает сам приёмник. Ключ — `<ID>.<endpoint приёмника>`, срок — 20 тиков: через 2 с срабатывает легаси-резерв. Конечная точка радио подключается при первом слове; речь ждёт подключения до 1 с. Машины и радио вне сети идут прежним путём.
- **Приёмник.** Приёмник (или all-in-one) передаёт тот же сигнал в легаси `receive_signal`, и дальше работают прежние правила:
  - выключенный, глухой к частоте или на другом уровне приёмник даёт `ignored`;
  - уже вышедший в эфир сигнал — `duplicate`;
  - сигнал, который легаси-резерв уже отправил обычной передачей, — `late`, и в эфир он второй раз не идёт;
  - неизвестный контекст — `expired`.
- **Потеря.** Если сигнал никто не ретранслировал и его не услышали, по истечении контекста он считается потерянным (`lost`). Отправитель об этом не узнаёт: так же было без телекомма.
- **Режим.** `NETDM_RADIO_MODE=authoritative` (у скриптов стенда — `-RadioMode`) или `set_authoritative()`. В этом режиме Shadow-выборка раздачи не идёт.
- **Скорость.** Команды речи уходят из очереди канала сразу (`flush_invokes`), не дожидаясь следующего тика подсистемы. В Host работают 64 провода за тик и первый переход при отправке. Пилот считает задержку целиком и по частям: ожидание в DM и путь от отправки до прихода на приёмник.

## P9.1 · кнопки и двери (Shadow)

### Схемы и команда

- `machine.door_set` v1 `{press, state?, bolted?, shocked?, id_scan?, safety?}`: `press` — ID нажатия (до 64 символов), `state` — `open` или `closed`, остальное — булевы. Значения абсолютные, переключателя нет. Поэтому повтор или дубликат команды не возвращает дверь назад: два одинаковых запроса не дают двойного переключения (матрица совместимости, строка «Управление»).
- `machine.door_state` v1 `{press, state, bolted?, changed, reason?}` — состояние двери после команды и причина, если она ничего не поменяла.
- Команда `machine.door/set_state`. Сервис `door.<endpoint>` предлагает каждая дверь.

### BlueMoon

- **Узлы.** Кнопка и её двери входят в сеть при первом нажатии этой кнопки. Кнопка `/obj/machinery/button` становится закреплённым узлом с конечной точкой. Каждый гермозатвор `/obj/machinery/door/poddoor` или шлюз — закреплённым узлом с сервисом `machine.door`. Первое нажатие ждёт их подключения до 3 с; его задержка считается отдельно (`cold`). Раньше двери и кнопки входили в сеть при инициализации, но на MetaStation это 1337 дверей и 411 кнопок, 1858 конечных точек. Старт раунда не успевал зарегистрировать датчики атмосферы, КПК и рации.
- **Нажатие.** Легаси-контроллер действует как раньше: находит двери по ID по всей станции и сразу их двигает. До его действия пилот теми же правилами находит цели и решение «открыть или закрыть». Двери берутся из `GLOB.airlocks`: там все двери, гермозатворы тоже, в порядке `GLOB.machines`, так что второго обхода всех машин станции нет. После действия болты, сканер ID, ток и защита шлюза читаются такими, какими их оставил легаси.
- **Команды.** Кнопка отправляет `set_state` каждой своей двери, как только та подключена. Ключ — `<press>.<endpoint двери>`, срок — 30 тиков, отправка сразу (`flush_invokes`). Дверь в Shadow только отмечает приход один раз и отвечает текущим состоянием с `reason=shadow`; повторная доставка считается дубликатом.
- **Сравнение.** Через 8 с по каждой паре «нажатие — дверь»: дошла команда по сети или промах с причиной (по пути: `not_attached`, `lane_full`, `door_gone`, `host_<ошибка>`; иначе исход команды из Host). Для дошедших отдельно считается, закончила ли легаси-дверь там, куда её поставило нажатие (`kept`, `differs`). Состояние снимается через 3 с после нажатия, когда легаси-двери доехали, а не в момент сравнения: иначе следующее нажатие той же кнопки его подменяет. Дверь без питания, заваренная или заблокированная откажет и авторитетной команде.
- **Авторитетный режим** включает `NETDM_DOOR_MODE=authoritative` или `doors.set_authoritative()`; по умолчанию Shadow. Нажатие не двигает двери: план даёт абсолютное состояние каждой двери (для шлюзов — куда ведут переключения болтов, сканера, тока и защиты), дверь применяет его при первом приходе команды и отвечает `changed`. Повтор отвечает `reason=duplicate` и не применяется. Невыполнимая часть даёт `reason=refused_<части>` (`bolts`: перерезаны провода или нет питания). Команда сохраняет режим нажатия, которое её отправило. Исключения совместимости идут легаси-путём в обоих режимах.
- **Исключения** считаются, но не зеркалятся: контроллер вне кнопки (`not_button`), контроллер шлюза без функций (`no_function`), нажатие без дверей (`no_doors`), больше 32 дверей (`fanout`). Массдрайверы, поджигатели, вспышки и остальные контроллеры идут прежним путём без зеркала.
- **Канал сервисов.** Канал обходит только конечные точки, чьё состояние Host может ещё не знать (`unsettled`): новые, с новым сервисом или подпиской, после ответа на свой запрос, после смены узла (`node_moved`) и после новой сессии. Раньше каждый проход подсистемы проверял все точки, а двери и кнопки добавили бы к 60 точкам ещё сотни.

## P9.2 · диагностика сети `network.diagnostics`

Сервис сетевого устройства (§7.6, §14.1). Устройство предлагает его обычной регистрацией, а отвечает за него Host, когда команда дошла до узла устройства по игровой сети, как у `research.server`. Состояния у сервиса нет: каждый ответ читается из опубликованного мира в момент прихода команды.

- **`link_state {reason?: inspect|refresh}`** → `network.link_state {state, wired, wiredUp, radio, devices, neighbors, more}`.
  - `state` — состояние самого устройства: `active`, `unpowered`, `broken`.
  - `wired` — число соседей по проектной разводке карты, `wiredUp` — сколько кабелей сейчас несут трафик.
  - `neighbors` — собственные порты устройства текстом `id:состояние,…`, не больше 16. `up` — кабель работает. Иначе названа причина: сосед `unpowered` или `broken`, либо `down` (само устройство выключено или сосед покинул мир). `more` — соседей больше, чем вошло в ответ.
  - `radio` — работает ли радиоточка, `devices` — сколько прочих узлов подключено к устройству кабелем.
- **`trace {node}`** → `network.trace {node, state: reachable|unreachable|unknown, hops, radioHops, cost, ticks}`. Один ограниченный поиск от устройства, не больше 20 000 раскрытых узлов. Исчерпанный бюджет отвечает `unreachable`. Узел задаётся десятичным ID.
- **State watch.** На экземпляр можно подписаться обычной подпиской на схему `network.link_state`. Пока у устройства есть подписчики, Host раз в 500 мс сравнивает его состояние с последним опубликованным и публикует только отличие, от имени устройства и с его узла.
  - Публикация идёт по игровой сети: подписчик, до которого сеть не дотягивается, ничего не узнаёт, а обесточенное устройство ничего не публикует.
  - Первая публикация приходит в пределах секунды после первой подписки. Новый подписчик уже наблюдаемого устройства получает состояние со следующим изменением, а текущее запрашивает командой `link_state`.
  - Одновременно Host ведёт не больше 64 наблюдаемых устройств. Отказ публикации (занято, превышен fan-out) повторяется на следующем проходе.
  - Устройство без подписчиков ничего не публикует.
- **Граница знания.** Устройство сообщает только о своих портах. Состояние остальной сети через него не читается; что лежит за мёртвым соседом, узнают на месте.
- **Проектная разводка.** Host хранит кабели и радиомосты карты отдельно от живых связей и публикует их одним неизменяемым объектом вместе со списком неактивных узлов. Он обновляется при публикации snapshot, обновлении карты и смене состояния узла, сбрасывается при `hello`.
- **Очередь Host.** Команды сервисов, которые исполняет Host, идут через одну ограниченную очередь (256). Тип сервиса выбирает исполнителя.

### BlueMoon

- Мультитул по АПЦ с закрытой панелью спрашивает сетевой модуль этого АПЦ. С открытой панелью мультитул по-прежнему работает с проводами. Без режима Observe поведение не меняется.
- АПЦ предлагает сервис при первом запросе: endpoint привязывается к узлу АПЦ в карте, экземпляр — `netdiag.<endpoint>`. Запрос — сетевая команда АПЦ самому себе, ответ приходит через Host.
- Отчёт в чат: состояние модуля, число кабелей и сколько из них на связи, радиоточка, подключённые устройства, и по строке на каждого соседа с названием его зоны и причиной («нет питания», «неисправен», «нет связи»).
- Модуль без питания или неисправный не отвечает: запрос не уходит, игрок видит «не отвечает». Запрос без ответа за 10 с завершается так же. Одновременно ждут не больше 32 запросов.
- Сервисный канал теперь умеет вести endpoint самого АПЦ, а не только устройства с компонентом узла.
- `trace` в BlueMoon пока не вызывается: нет игрового способа выбрать цель.
- State watch: `watch(наблюдатель, АПЦ)` подписывает любой сетевой узел на состояние АПЦ и хранит последнее пришедшее состояние с временем прихода. Игрового потребителя пока нет: нужен экран или консоль, это решение об интерфейсе. Одновременно наблюдается не больше 64 АПЦ.

## P10 · запросы к сети `network.query`

Сервис сетевого устройства (§14.5). Запрос — команда сервиса: он доходит до узла устройства по игровой сети, Host отвечает от имени устройства, ответ возвращается по сети. Глобального запроса «ко всей станции» у игрока нет.

- **`services {type?, limit?, cursor?, prefix?, maxHops?, projection?}`** → `query.page {status, revision, count, items, cursor?}`. Каталог сервисов.
  - В ответ входят сервисы, которые спрашивающий вправе обнаружить (политика discover) и до провайдера которых устройство сейчас дотягивается по сети. Скрытый сервис и отрезанный сервис просто отсутствуют: запрос не сообщает, что они существуют.
  - `items` — текст `instance|serviceType|hops,…` в порядке имён экземпляров. `hops` считается от устройства, отвечающего на запрос. `type` — точное имя типа.
  - `limit` — от 1 до 16, по умолчанию 8.
  - `prefix` — только экземпляры, чьё имя начинается с него. Ограничивает сами диапазоны индекса, поэтому бюджет просмотра не тратится на чужие имена.
  - `maxHops` — от 0 до 64: только сервисы не дальше этого числа хопов от отвечающего устройства (0 — его собственные).
  - `projection` — `full` (по умолчанию, `instance|serviceType|hops`), `instance_type` (`instance|serviceType`) или `instance`.
- **Статус полноты:** `complete` означает конец списка, `partial` содержит курсор продолжения, `empty` означает пустую первую страницу. `snapshot_expired` требует начать заново после смены ревизии или истечения срока. `invalid_cursor` означает повреждённый курсор или несовпадение параметров запроса. `budget_exhausted` означает, что обход сети не завершился в пределах бюджета.
- **Курсор** непрозрачный и действует 60 секунд. Host привязывает его к текущей сессии, экземпляру запроса, узлу и поколению отвечающего endpoint, ID и поколению спрашивающего, типу, эффективному лимиту, префиксу, `maxHops` и проекции. Ревизия растёт при изменении состава каталога, узла или домена провайдера.
- **Бюджеты одной страницы.** Индекс видимости и типа даёт до 64 записей на просмотр с позиции курсора. Затем выполняется один поиск достижимости до 20 000 узлов. Ответ содержит до 16 элементов и занимает до 4 КиБ. Страница может быть `partial` с нулём элементов, если просмотренные записи недостижимы.
- **Достижимость** считается на момент страницы и к ревизии не привязана: между страницами сеть может измениться.
- **`schema {instance}`** → `query.schema {status, instance?, serviceType?, schema?, major?, minor?, commands?}`. Читает зарегистрированный контракт экземпляра по точному имени. `commands` содержит имена команд через запятую. Их вызов по-прежнему проверяет `Invoke` на целевом сервисе.
- **`state {instance}`** → `query.state {status, instance?, publication?, sequence?}`. Читает метаданные публикации: `idle` и `"0"` до первой принятой публикации, затем `published` и её номер десятичной строкой. Для этого нужны права обнаружения и подписки на целевой экземпляр. Данные публикации и результаты её доставки остаются в профильном сервисе.
- **`route {instance}`** → `query.route {status, instance?, hops?, radioHops?, path?}`. Путь пакета от отвечающего устройства до узла сервиса сейчас: `path` — элементы `узел:связь` через запятую, первая связь `start`, затем `cable` или `radio`. После 32 узлов путь обрезается со статусом `partial`. Сервис, который спрашивающий не может обнаружить, — `empty`; обнаружимый, но недостижимый — `unreachable`. Один ограниченный поиск, как у `trace`.
- **`jobs {limit?}`** → `query.jobs {status, count, items}`. Последние команды спрашивающего, новые первыми: элементы `операция|экземпляр|команда|исход|результат`. Хранятся последние 16 операций каждого endpoint, показываются только операции его текущего поколения. Сам запрос `jobs` в список не входит.
- В обоих точечных запросах `complete` содержит снимок на момент ответа АПЦ. При отсутствии подтверждённого пути в пределах бюджета поиска, скрытой или отсутствующей цели ответ содержит только `status = empty`. Некорректное имя даёт `invalid_request`. Запрос и ответ идут между спрашивающим и АПЦ, который читает свой достижимый каталог.
- **WatchQuery.** Экземпляр регистрируется со схемой `query.directory {services, digest, partial}`, и на него можно подписаться. Пока есть подписчики, Host не чаще раза в 500 мс пересчитывает набор сервисов, до которых устройство дотягивается, и публикует состояние только при изменении. Пересчёт идёт, только когда изменились версия мира, ревизия каталога, отчёт проводки или набор наблюдаемых устройств; без изменений — раз в 30 с. Так же устроено наблюдение портов `network.diagnostics` (версия мира и отчёт проводки).
  - Публикация сообщает число сервисов и digest их имён. Самих имён в ней нет: подписчик, заметив новый digest, повторяет запрос `services`.
  - Набор считается глазами самого устройства (что вправе обнаружить его endpoint). Политика подписки по умолчанию пускает только домен устройства, поэтому наблюдатель не узнаёт об изменении того, чего не увидел бы запросом. Экземпляр с открытой подпиской эту границу ослабляет.
  - Ревизия каталога в состояние не входит: сервис вне досягаемости набор не меняет.
  - Бюджеты: не больше 16 наблюдаемых каталогов, 256 записей на проход (иначе `partial`), один поиск достижимости до 20 000 узлов на каталог.
  - Публикация идёт по игровой сети с узла устройства, как у `network.diagnostics`.

### BlueMoon

`diagnostics.query_services(узел, АПЦ, тип, callback, limit, cursor)`: сетевой узел спрашивает АПЦ. АПЦ предлагает сервис `netquery.<endpoint>` при первом запросе. Callback получает страницу: статус, ревизию, курсор и элементы `{instance, type, hops}`. Без ответа за 10 с статус `no_answer`. Одновременно ждут не больше 32 запросов. `diagnostics.watch_services(узел, АПЦ)` подписывает узел на изменения каталога этого АПЦ; последнее состояние лежит в `directory_states`. Игрового экрана пока нет.

`diagnostics.query_schema(узел, АПЦ, экземпляр, callback)` и `diagnostics.query_state(узел, АПЦ, экземпляр, callback)` используют ту же очередь и тот же timeout. Callback получает DTO команды или `refused`/`no_answer`. При завершении или истечении запроса удаляется связка с ID сетевой операции.

R&D в авторитетном режиме дочитывает каталог `research.server` до конца и выбирает доступный сервер своего techweb с минимумом переходов. При равенстве выбирается первое имя по порядку каталога. После истечения или отклонения курсора поиск один раз начинает обход заново.

## P11 · оболочка сети `network.shell` (первый срез)

Сервис сетевого устройства (§14.6). `run {line}` исполняет один конвейер, а `run_script {source}` выполняет многострочный скрипт на устройстве, до которого дошёл запрос. Обе команды возвращают `shell.output {status, count, fuel, rows, error?, position?}`.

- **Строка** — конвейер: команда-источник, затем фильтры `where <поле> -eq|-ne|-lt|-le|-gt|-ge|-like <значение>`, `select`, `sort <поле> [-desc]`, `first N`, `last N`, `count`. Аргументы: `-имя значение`, `имя=значение`, позиционные; текст в кавычках.
- **Источники:** `services [-type T] [-prefix P] [-hops N]` → `{instance, type, hops}` (`-hops` от 0 до 64); `links` → `{node, state}`; `self` → `{node, state, wired, wiredUp, radio, devices}`; `trace <node>` → `{node, state, hops, radioHops, ticks}`; `route <instance>` → `{hop, node, link}` по узлам пути (недостижимый сервис — одна запись с `link=unreachable`, скрытый — ни одной); `jobs` → `{operation, instance, command, outcome, result, reason}` без самой строки.
- **Права.** У строки нет собственных прав. Каталог читается глазами спрашивающего (политика discover), достижимость считается от устройства.
- **`invoke`** — единственная команда действия. Она стоит последней стадией или одна в строке: `invoke <экземпляр> <команда> имя=значение…` либо `… | invoke <команда> имя=значение…` для поля `instance` каждой записи.
  - Команда уходит как обычная команда сервиса от имени спрашивающего и с его узла: с его правами, квотами и маршрутом. Устройство, исполняющее строку, ничего своего не добавляет.
  - Строка не ждёт ответа. На каждую цель она возвращает запись `{instance, command, status, operation}`: `sent` либо код отказа (`unknown_service`, `forbidden`, `invalid_payload` и другие). Результат команды приходит спрашивающему по сети, как у любой команды.
  - На запуск выделено четыре цели. Если целый вход стадии выходит за остаток бюджета, эта стадия отвечает `limit_exceeded`. Каждая цель стоит 64 единицы топлива, списываемые до отправки.
  - Сервис, которого спрашивающий не видит, отвечает `unknown_service`. Строка не может запускать другие строки: `invoke` на `network.shell` отвечает `forbidden`.
  - Повтор сетевого запроса с тем же ключом идемпотентности возвращает результат исходной операции. Ключ дочерней команды учитывает ID доставки запроса и номер цели.
- **`rows`** — записи текстом `имя=значение,имя=значение;…`. Разделители в значениях заменяются пробелом.
- **Скрипт.** Каждая строка содержит конвейер, `if <конвейер>` или `end`. Условие читает сеть и выполняет блок, если получена хотя бы одна запись. Вывод даёт последний исполненный конвейер вне условий. Скрипт проверяет синтаксис и структуру блоков до первого обращения к сети. Если ошибка возникает во время исполнения, уже отправленные команды продолжают доставляться.
- **Статусы:** `ok`, `parse_error`, `unknown_command`, `invalid_argument`, `fuel_exhausted`, `limit_exceeded`, `source_failed`. При отказе приложены `error` и `position` с отсчётом от начала строки или скрипта, начиная с нуля.
- **Границы.** Строка до 1024 символов, до 12 стадий и 16 аргументов, до 64 записей. Скрипт до 2048 символов и 12 строк, JSON запроса до 8 КиБ, глубина вложенности `if` до 4. На запуск 4096 единиц топлива, до двух обходов сети суммарно для `services`, `trace` и `route`, ответ до 4096 символов.

### BlueMoon

Мультитул на закрытом АПЦ открывает терминал его сетевого модуля. Кнопка «Скрипт» открывает редактор. Несохранённый текст живёт до закрытия окна. Другие игровые устройства могут передать свой сетевой узел в `diagnostics.run_script(узел, АПЦ, source, callback)`. При сбросе сессии Host уже отправленный запуск заканчивается статусом `no_answer`, поскольку его команды могли уйти до сброса.

Во вкладке «Скрипт» можно сохранить исходник в файл `netdm.NDS1` на обычном Data Disk из импринтера. Для каждого действия терминал проверяет, что тот же диск по-прежнему в руках. Запись использует свободное место штатной файловой системы диска. «В редактор» загружает текст, а «Запустить с диска» отправляет сохранённый исходник через `run_script` от имени устройства терминала. У версии NDS1 один файл терминала на диск.

На включённом КПК в руках в меню приложений доступен «Сетевой терминал». КПК вызывает свою оболочку на собственном endpoint, а поиск сервисов и `invoke` используют его текущий радиомаршрут. У мобильной оболочки `Discover`, `Subscribe` и `Invoke` доступны владельцу endpoint. Data Disk можно держать во второй руке. Если выключить КПК или убрать его из рук, окно закрывается и ожидающие отправки из него прекращаются.

Сетевой имплант доступен через чертёж в «Neural Programming». После установки действие «Сетевой терминал» открывает ту же оболочку. Радиоузел принадлежит импланту и следует за носителем. При извлечении узел снимается с сети. Терминал поддерживает Data Disk в руке.

Проводной адаптер печатается в автолате. Подключение требует физической близости к АПЦ или закреплённому сетевому устройству. Для машины нужен открытый сервисный люк. Адаптер получает собственный endpoint и проводной порт к АПЦ сегмента на клетке подключения. На сегменте без АПЦ адаптер остаётся изолирован. ЛКМ по установленному адаптеру открывает терминал, Alt+ЛКМ отключает адаптер. При перемещении или удалении цели узел адаптера снимается с сети.

- **Переменные скрипта (`run_script`).** `$имя = конвейер` сохраняет записи строки; `$имя` допустим только первой стадией и аргументов не принимает. Имя — латинская буква, затем буквы, цифры и `_`, до 32 символов. Чтение незаданной выше переменной — `parse_error` с позицией; переменная из пропущенного блока `if` пуста. До 8 переменных на скрипт, чтение стоит `1 + число записей` топлива. В команде `run` переменных нет (`invalid_argument`).

- **Программы.** `start {name, source}` → `shell.program {status, program?, error?, position?}`; `stop {program}` → тот же ответ. Статусы: `started`, `stopped`, `unknown_program`, `parse_error`, `unknown_command`, `invalid_argument`, `limit_exceeded`.
  - Текст: необязательная первая строка `on <конвейер только для чтения>`, затем скрипт; строка `wait` отдельно делит его на фазы (до 4).
  - `$event` — записи конвейера правила в момент срабатывания; `$result` — записи команд предыдущей фазы с полем `outcome`.
  - Строка-источник `programs` → `{program, name, state, runs, fuel, memory, reason}` для программ спрашивающего на этом устройстве; `memory` — сколько символов держит программа.
  - Первая строка `every <секунды>` (10–3600) делает программу таймером: фазы выполняются сразу и затем раз в N секунд, `$event` пуст, предел 100 запусков.
  - `$state` — собственное состояние программы: фаза присваивает `$state = конвейер`, следующие фазы и запуски читают `$state`. Сохраняется вместе с программой.
  - Бюджет состояния: `$state`, `$event`, `$result`, команды фазы и последнее наблюдение правила вместе — не больше 4096 символов (`NetDM:ProgramStateBytes`, 256–65 536). Программа сверх бюджета — `faulted` с причиной, состояние не обрезается.
  - **Знание оператора (P12.1).** `scan {radius?}` → `shell.scan {status, revision, nodes, links, services, retryAfter?}`: с узла устройства, чья оболочка отвечает, оператор (спрашивающий endpoint) узнаёт ретрансляторы (АПЦ) в пределах `radius` хопов (1–8, по умолчанию 3, не больше 256 узлов, иначе `partial`) по живым связям, проводным и радио; кабельные порты этих ретрансляторов к известным узлам с состоянием (`up`, `unpowered`, `broken`, `down`); сервисы, которые оператор вправе обнаружить, на узлах в этой окрестности, и провод их устройства к ретранслятору. Скрытое не записывается. Не чаще раза в 10 с на оператора (`busy` с `retryAfter`). Известное в окрестности, но не найденное теперь, становится устаревшим.
  - `knowledge {since?, limit?}` → `shell.knowledge {status, revision, count, items}`: изменения знания после ревизии `since`, по порядку, до 64 элементов и 3600 символов (`partial`, продолжение — с выданной `revision`). Элементы: `n|id|relay или device|x|y|z`, `l|a|b|состояние`, `s|экземпляр|тип|узел`, к каждому `|возраст в секундах|fresh` или `|…|stale`; `r|<ключ>` — забытый элемент. `reset` — читать заново с `since=0`. Свежесть по Р3: элемент свежий 60 с после подтверждения сканированием и устаревает сразу, когда устройство, с которого оператор сканировал последний раз, больше до него не дотягивается (проверяется при чтении после изменения мира или проводки). Устаревание по времени ревизию не меняет: клиент считает его по возрасту. Знание хранится в памяти Host до конца его процесса; до 64 операторов, у каждого до 512 узлов, 1024 связей и 512 сервисов, лишнее забывается начиная с давно устаревшего.
  - **Присутствие (P12.2).** `enter`, `detach`, `leave`, `presence` (`shell.presence_request {note?}`) → `shell.presence {status, presence?, host?, generation?, state?, reason?}`. Одно присутствие на оператора (спрашивающий endpoint): `enter` создаёт его на устройстве отвечающей оболочки (`entered`) или возвращает существующее, где бы оно ни стояло (`present`, после `detach` — `resumed`). Не больше 64 присутствий и 4 на устройство (`limit_exceeded`). Состояния `active`, `suspended`, `ended`; причины по Р6: `operator_away` (`detach`; через 5 минут — `operator_gone` и конец), `entry_lost` (endpoint оператора исчез; через 60 с — конец), `host_unpowered`, `host_unreachable` (новый runtime, 60 с на возврат), `host_lost` (оболочка хоста ушла — конец без копии), `left`. Завершённое присутствие сообщается до следующего `enter`.
  - `act {line}` → `shell.output`: строка выполняется на хосте присутствия с правами оператора (видимость — оператора, достижимость — хоста), как строка программы. Нужно активное присутствие (`no_presence`, `suspended`) и маршрут от отвечающего устройства до хоста (`out_of_reach`). `scan` при наличии присутствия сканирует с его хоста (`suspended`, `out_of_reach` в `shell.scan`), каталог читается как каталог оператора. Присутствия живут в памяти процесса Host.
  - **Переход (P12.3).** `move {to}` → `shell.presence {status=moving, to, arriveIn, …}`: активное присутствие, которым оператор управляет, уходит в оболочку другого устройства, которую оператор видит и может вызвать (`forbidden`), по существующему маршруту (`unreachable`), если там меньше 4 присутствий (`limit_exceeded`); `invalid_argument` — тот же хост. Время пути — 1 с на хоп, от 1 до 15 с. В пути состояние `moving`, `host` пуст: присутствие не исполняется нигде, `act` и `scan` отвечают `moving`. Маршрут от исходного хоста до цели проверяется каждый проход; оборвался или цель ушла — присутствие возвращается на исходный хост с причиной `returned: route_lost`, а если исходного хоста нет — завершается (`lost_in_transit`). По прибытии хостом становится цель, `generation` растёт на 1.
  - **Сетевая сущность.** Программа — сущность: `programs` показывает `generation` и `revision`. `migrate {program, to}` → `shell.program {status, program, to?, generation?, error?}`: владелец переносит свою программу в оболочку другого устройства (`to` — экземпляр `network.shell`). Перенос разрешён, если цель видна владельцу и он может её вызвать (`forbidden`), она достижима по сети от исходного устройства (`unreachable`), на ней есть место (`limit_exceeded`) и программа не ждёт исхода своих команд (`busy`). Состояние, `$state`, фаза и счётчики переносятся. Старая копия становится `migrated` с причиной `moved to <to>` и не исполняется. Новая копия получает `generation + 1`, не хранится на носителе цели и сразу проходит правило или таймер. Права не расширяются: публиковать на новом устройстве она может, только если владелец и есть это устройство.
  - `start {…, ensure, entity?}`: носитель, который называет программу номером `entity` (или без номера — тем же устройством, владельцем и текстом), после её переноса получает `moved {program, to, generation}`; BlueMoon убирает такую программу с носителя. Носитель запоминает номер из ответа `started`/`running`. Узел устройства с сохранёнными программами сразу заводит endpoint, чтобы подключение запустило их без участия игрока.
  - В терминале BlueMoon строка `migrate <номер> <экземпляр оболочки>` отправляет `migrate`.
  - `… | publish` публикует записи как очередную публикацию `shell.output {status, count, fuel, rows}` сервиса оболочки устройства, подписчики получают её как публикацию любого сервиса. Публиковать может только само устройство: программа, владелец которой — endpoint устройства, или строка, которую устройство запустило само. Строка, которую прислал другой endpoint, получает `status=forbidden`. Публикация считается действием в бюджете устройства.
  - Ключи идемпотентности команд программы выводятся из сессии, номера программы, срабатывания и фазы.
  - В BlueMoon программы запускаются из редактора на АПЦ, КПК, импланте и подключённом адаптере. Кнопка «Программы» запрашивает актуальный список. Программа привязана к поколениям обоих endpoint и прекращает работу при утрате доступа.
  - КПК передаёт в `device_state` опциональный `executionPowered`. При выключении или штатном отключении из-за разряда Host приостанавливает фоновое выполнение, сохраняя ID программы, фазу и последнее наблюдение правила. Включение возобновляет выполнение. Экран влияет на доступ к редактору. Радио и входящие сообщения сохраняют режим ожидания. Для старых отправителей факта действуют обычные `powered` и `operational`.
  - Пока программа приостановлена, её бюджет ожидания фазы заморожен. Уже отправленные сетевые операции продолжают доставляться или истекать по собственным срокам.
  - Бюджет устройства на минуту: 16 384 топлива и 32 попытки команд на все его программы. Сверх бюджета программа в состоянии `throttled` до конца минуты и продолжает с того же места. Правило после срабатывания ждёт 5 с.
  - Правило вычисляется заново, только когда изменилось то, что оно читает, не чаще раза в секунду: версия мира и отчёт проводки всегда, ревизия каталога для `services` и `route`, видимое состояние программ (без топлива) для `programs`, ревизия операций владельца для `jobs`. Без изменений — раз в 30 с.
  - `start {name, source, ensure: true}` — запуск с носителя устройства. Если у того же endpoint-а (того же или нового поколения) уже идёт незавершённая программа с этим именем и тем же текстом, ответ `running` с её номером, состояние сохраняется. Другой текст заменяет программу. Старое поколение не может забрать программу у нового (`invalid_argument`). Программа, запущенная с `ensure`, после ухода endpoint-а ждёт его 60 с.
  - BlueMoon хранит до 4 таких программ: на КПК в файле `netdm_programs.NDP1` на диске, на импланте, адаптере и АПЦ — в памяти предмета. Запускает их при каждом успешном `endpoint_attach`.
  - Сохранение: `programs-<round>.json` рядом с журналом исследований. Всё, от чего зависит восстановление, записывается сразу (все фазы прохода отмечаются одной записью до запуска); топливо, причины и последние наблюдения — не чаще раза в 5 с. Файл пишется через временный файл и переименование, без принудительного сброса на диск. Новый runtime и новый процесс Host того же раунда сохраняют программы; endpoint-ам даётся 60 с вернуться. Ожидание через перезапуск заканчивается `unknown`, прерванная фаза не повторяется.
