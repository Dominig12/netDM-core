# ADR-0001. Размещение NETRUN: библиотеки рядом с транспортом, один composition root

*Статус:* принято 25.11.2026.
*Контекст:* §3 спецификации рисует `NetDM.Host` и `NetRun.*` как отдельные единицы. Исполняемый проект сегодня называется `NetDM.Host`; его имя зашито в `deploy/bluemoon/Host.Dockerfile`, в Windows-комплекте (`Build-WindowsBundle.ps1`), в `scripts/check-all.ps1`, `scripts/test-bluemoon-unit.ps1` и в документации стенда.

*Решение:*
1. Вводим библиотечные проекты `NetRun.Core`, затем `NetRun.Runtime`, `NetRun.Observability`, `NetRun.Content` — по мере появления в них кода.
2. Зависимости направлены только от NETRUN к NETDM: `NetRun.*` → `NetDM.Core`/`NetDM.Services`.
3. Единственный процесс — по-прежнему `NetDM.Host`. Он остаётся composition root и единственным местом, где собираются зависимости обоих слоёв.
4. Второй процесс, отдельный порт IPC и второй мост не создаются.

*Альтернативы:*
- Переименовать `NetDM.Host` → `NetRun.Host`. Отклонено: ломает поставку и скрипты, не даёт функциональной выгоды, а §3.146 прямо допускает иные имена при сохранении границ.
- Отдельный `NetRun.Host` процесс. Отклонено: потребовал бы второго IPC-канала и второго нативного шима на каждый мир, удвоил бы задержку commit и нарушил бы BRIDGE-001 (одна точка отказа вместо двух).

*Последствия:* имя проекта историческое; границы слоёв обеспечиваются направлением ссылок и проверяются на ревью. Если позже понадобится вынести NETRUN в отдельный процесс, это делается за `NetRun.Host` без изменения библиотек.

# ADR-0002. Один логический writer для домена NETRUN

*Статус:* принято 25.11.2026.
*Контекст:* ARCH-003 требует одного писателя на область авторитетного состояния и запрещает защищать составные инварианты одиночными `lock`/`ConcurrentDictionary`. В транспорте это уже соблюдено (`ServiceRuntime._gate`, `RadioPacketTransport._gate`).

*Решение:* `NetRun.Core` строится как набор владельцев доменов (`HostRegistry`, `ResourceLedger`, `CapabilityAuthority`, `ActionRegistry`, `EffectRegistry`), каждый — с одним логическим writer'ом. Публичные операции синхронны и не удерживают блокировку через `await`/IO. Долгие операции выносятся в планировщик как намерения (`ActionPlan`), которые владелец повторно валидирует и фиксирует.

*Последствия:* многопоточность достигается параллелизмом чтения иммутабельных снимков и вычислений в `PriorityWorkScheduler`, а не параллельной записью. Шардирование по доменам допускается только после измерения насыщения (см. §17.1 спецификации).

# ADR-0003. Реестр действий как единственный источник правды о действии

*Статус:* принято 25.11.2026.
*Контекст:* SVC-001 требует, чтобы описание операции содержало ID, версию, типы, права, стоимость, дальность, cooldown и документацию, а PRIM-001 — чтобы игрок, NPC, терминал и VM пользовались одним реестром.

*Решение:* `ActionRegistry` в `NetRun.Core` хранит `ActionDescriptor` и реализацию `IGameAction<TArgs,TResult>`. Дескриптор содержит: стабильный ID и версию, категорию (`Perception`, `Connectivity`, `Data`, `Programs`, `Resources`, `Security`, `Effects`, `Execution`), вид (`Query`/`Command`/`Event`/`Transfer`), требуемую capability, стоимость CU, cooldown, дальность в хопах, отображаемое имя, описание и схему аргументов. Контекстные действия в UI, справка и блоки конструктора формируются из дескриптора; собственная копия параметров в UI или скрипте невозможна.

*Последствия:* новый эффект или способность добавляются регистрацией, а не правкой UI или транспорта (ARCH-002). Cooldown принадлежит исполнителю и группе примитивов, а не файлу программы (AT-15).

# ADR-0004. Сборка и проверки без `.sln` и без фреймворка тестов

*Статус:* принято 25.11.2026.
*Контекст:* в репозитории нет `.sln` и нет xUnit/NUnit; smoke-тесты — консольный `Main` с `Console.WriteLine`. `dotnet build` в корне падает с `MSB1003`. Существующие проверки воспроизводимы и приняты.

*Решение:* сохраняем модель. Новый проект тестов `tests/NetRun.Tests` повторяет стиль `NetDM.SmokeTests`: консольное приложение, маркер завершения, exit code. Сборка — по csproj: `dotnet build src/NetDM.Host -c Release` и `dotnet run --project tests/NetRun.Tests -c Release`.

*Отклонения:* `.sln` не вводится, потому что он изменил бы точку входа сборки в скриптах и CI без выгоды. Тестовый фреймворк не вводится, потому что `Directory.Build.props` включает `TreatWarningsAsErrors`, а любая зависимость добавила бы внешний пакет, которого сейчас в решении нет вовсе.

*Последствия:* отчётность — текстовые маркеры; подмножество тестов запускается аргументом командной строки.

# ADR-0005. Совместимость с существующим миром: без Docker и без живого DreamDaemon

*Статус:* принято 25.11.2026 по указанию владельца («давай пока без докера»).
*Контекст:* на стенде отсутствуют C/C++ тулчейн (`cl.exe`, `gcc`, `mingw`, `clang`, `zig`) и работающий Docker-демон, поэтому `netdm_byond.dll` собрать нельзя, моста в дереве нет. Любая проверка в живом DreamDaemon невозможна.

*Решение:* этапы принимаются по трём каналам: (1) C#-сборка без предупреждений, (2) юнит/smoke-харнесс и живой Host через `tests/host-ipc.ps1`, (3) компиляция DM без ошибок и предупреждений. Требования, для которых нужен живой мир, помечаются в [status.md](status.md) как «не проверено — блокер стенда» и **не объявляются выполненными**.

*Последствия:* этап не считается полностью принятым без указанной пометки; при появлении тулчейна прогоняются `scripts/test-byond-world.ps1` и `scripts/test-bluemoon-unit.ps1`.

# ADR-0006. Виртуальные ресурсы — отдельная модель, не реальный CPU

*Статус:* принято 25.11.2026.
*Контекст:* §10 требует, чтобы CU/RAM/Storage/Bandwidth были игровыми величинами с авторитетным учётом, а §2.5 запрещает переносить реальную вычислительную физику в C#.

*Решение:* `ResourceLedger` учитывает игровые величины на монотонном игровом времени с фиксированным шагом. Реальные потоки, `Environment.ProcessorCount` и тайминги планировщика не участвуют в расчёте CU. Восстановление начисляется один раз за интервал; повторное начисление за тот же интервал невозможно, потому что шаг времени двигает владелец.

*Последствия:* баланс настраивается конфигурацией и плейтестом; числа в коде — стартовые ориентиры, а не SLA.
