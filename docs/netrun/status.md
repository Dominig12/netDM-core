## 3. N3. Первое действие до физического мира — частично выполнено

Реализовано и проверено:

| Что | Где | Поведение |
|---|---|---|
| Удалённые действия | `NetRun.Core/Actions.cs` (`IRemoteGameAction`, `INetRunDispatchScope`, `INetRunTransport`, `ActionStatus.Accepted`) | `Commit` удалённого действия только отправляет намерение; операция остаётся `Accepted` до отчёта цели; попадание в commit = подтверждение цели, а не отправка |

## 4. Модель знания и наблюдения — выполнено

Реализовано (§9.4, PRIM-002, AT-12):

| Что | Где | Поведение |
|---|---|---|
| Уровни знания | `NetRun.Core/Knowledge.cs` | `Unknown → Anomaly → Observed → Identified`; уровни не обязательная последовательность, наблюдение только повышает знание |
| Хранилище | `KnowledgeStore` | На наблюдателя, ограничено (`MaxPerObserver = 1024`), вытесняет самую старую запись; старение по игровому времени: `StaleAfter = 60 с`, `ForgetAfter = 600 с` |
| Свежесть | `Holds(..., requireFresh)` | Устаревшая запись остаётся знанием, но не даёт права действовать; проекция показывает `stale` явно |
| Забывание | `Forget(host)`, `ForgetObserver`, `Prune` | Уничтожение хоста стирает знание о нём; сессия наблюдателя стирает всё его знание |
| Запись знания | `net.scan` пишет `Observed` для достигнутых целей; `net.inspect` подтверждает запись | Знание начинается с действия, а не с факта существования объекта |
| Гейт восприятия | `net.inspect` | Цель, которую наблюдатель не знает, отвечает как несуществующая; свой хост осмотра не требует |
| Проекция знания | `netrun_knowledge` | `host`, `level`, `confidence`, `ageMs`, `stale` — история наблюдений без имён |
| Проекция мира для клиента | `netrun_view` | только хосты, о которых наблюдатель что-то знает; имя появляется лишь при `Identified`, при `Observed` виден только класс; `stale` и `available` показаны явно. `netrun_state` остаётся инструментом разработчика и в клиент не идёт |
| Установление личности | `net.inspect` | успешный осмотр поднимает запись до `Identified`; повторный `net.scan` её не понижает |

Единый ответ на неизвестную цель: конвейер больше не отказывает по отсутствию цели до валидации. Порядок стал
`право на исполнение → идемпотентность → право на цель → валидация → cooldown → резерв`. Это убирает разницу между «объекта нет» и «объект скрыт от тебя» на уровне восприятия и сохраняет `TargetDestroyed` для честно уничтоженных целей физических действий.

## 6. Точка расширения контрактов — механизм сделан реальным (D-07, частично)

`SchemaRegistry.CreateDefault` больше не содержит привилегированного списка: встроенные контракты зарегистрированы теми же `IServiceContractModule`, что и любой игровой модуль (`SchemaRegistry.BuiltinContractModules`, 10 модулей). Новый сервис добавляется регистрацией модуля в composition root, а не правкой реестра.

Проверки: `ServiceSmokeTests` — «every built-in domain is a module», «the built-in modules register the stable protocol on their own» (`machine.door/set_state`, `atmos.sample`, `network.shell/run`), «duplicate feature contracts must be rejected, not overwritten».

Осталось: перенос самих игровых контрактов SS13 из `NetDM.Services/Contracts` в `NetRun.Content` — это меняет размещение модулей, а не механизм, и делается вместе с DM-интеграцией.

## 7. Взлом как игровая операция (§9.2) — выполнено

| Что | Где | Поведение |
|---|---|---|
| Режимы | `NetRun.Core/Breach.cs` | `security.breach.stealth`, `.normal`, `.forced`; сила 1/2/3 против сложности `Open=0`, `Standard=1`, `Secure=2`, `Quarantine=3`. Успех — сравнение силы со сложностью, решает сервер, а не скрипт |
| Цена | дескриптор действия | 3/5/8 CU, общий cooldown `security.breach` 4 с: перебором режимов доступ не нафармить |
| Результат | `Commit` | при успехе выдаётся обычный capability с `GrantSource.Breach` на 90 с (45 с форсированный); он истекает и отзывается как любой другой |

## 19b. Эффекты больше не инертны (PRIM-003) — выполнено

Самое тяжёлое из найденного аудитом: ранее `Damage`, `Drain`, `Repair` и `Shield` записывались как эффекты и **не меняли ни одного числа**. Теперь:

| Эффект | Что меняет |
|---|---|
| `Drain` | реально снимает compute с буфера цели через леджер; больше, чем есть, взять нельзя — остаток не уходит в минус |
| `Damage` | снижает целостность цифрового ядра, живущего на этом хосте (эффект бьёт по хосту, не по имени) |
| `Shield` | уменьшает входящий `Damage` на свою величину, не ниже одного пункта |
| `Repair` | восстанавливает целостность ядра, не выше полной |
| Прочие | остаются живыми для читателей и рапортуют свою величину |

`EffectResult.Applied` теперь говорит, **что действительно произошло**: 0 — эффект подошёл по определению, но менять было нечего. Это закрывает и «фиктивный успех»: результат не выдаёт запись за воздействие.

Проверки: `dotnet run --project tests/NetRun.Tests -c Release` — PASS, **407 утверждений** (новый раздел `effect consequences`): слив уменьшает буфер и не уходит в минус; урон снижает целостность ровно на величину; щит уменьшает следующий урон; ремонт восстанавливает только недостающее; урон по хосту без ядра и слив с хоста без compute дают `Applied = 0`.

`scripts/check-all.ps1 -Only host` — PASS целиком (3 + 8 + 3 + 127 с).

Осталось по PRIM-003: дальность (`RangeHops`) всё ещё объявлена и не проверяется — нужен счётчик хопов от транспорта и отказ `out_of_range` на границе `Prepare`.
## 19c. Дальность действия проверяется (PRIM-003, §8.2)

`RangeHops` был объявлен, сериализовался в интерфейс и не проверялся: один грант действовал на любой хост. Теперь `IHopDistance` даёт расстояние от транспорта, а `ActionPipeline.Prepare` отказывает до резерва и cooldown: недостижимо — `OutOfRange/"no_route"`, дальше объявленного радиуса — `OutOfRange/"range"`. `net.inspect` — 8 хопов, `net.scan` — 12, проверка идёт по объявлению каждого действия. Проверено разделом `range`.

## 19d. Присутствие и движение (PLAY-001)

`PresenceRegistry`: присутствие стоит на одном хосте и требует, чтобы хост реально держал его ядро; маршрут планирует транспорт (`IRoutePlanner`); во время перехода действовать нельзя; прибытие — только в назначенное время и с повторной проверкой маршрута; разрыв маршрута возвращает присутствие назад — телепорта нет; отмена; потеря хоста. Проверено разделом `presence`.

## 19e. Граница commit и оракул существования

Операция, разрешённая профилем хоста, проходила commit без повторной проверки — теперь решение принимается заново, и ужесточение политики между подготовкой и фиксацией останавливает её. Отказ унифицирован: отсутствующая цель, чужая цель и запрещающая политика отвечают одинаково (`Forbidden/"denied"`), поэтому перебором идентификаторов нельзя узнать о существовании хоста. Проверено разделом `invariants`.

## 19f. Импорт ≠ запуск (SCRIPT-003) и журнал идемпотентности (SVC-002)

Первый вызов `netrun_program` компилирует и описывает программу (`confirmation_required` и дайджест текста), запуск — отдельный вызов `confirm = true`, а кнопка в окне — осознанное действие игрока. Журнал идемпотентности больше не очищается целиком: ключи вытесняются по одному, а при исчерпанном окне неизвестный ключ получает `UnknownOutcome` вместо нового исполнения. Проверено живым `host-ipc`.

## 19g. LIFE-001 доведён до действий и до IPC

`ActionRequest` несёт личность и поколение управления, `Prepare` отказывает старому поколению (`Forbidden/"life_generation"`). Операция `netrun_life`: `create`, `migrate`, `migrate_commit`, `migrate_cancel`, `backup`, `restore`, `restore_backup`; идентичность раунда выделяет хост, а не клиент. Проверено разделом `invariants` и живым `host-ipc`: создание, копия, перенос с новым поколением, отказ отработавшему.

## 19h. Принятая работа не теряется при перегрузке (P5, §6.3)

Отказ транспорта по ёмкости больше не завершает доставку как `Busy`: она возвращается в outbox и предлагается снова. Повтор ограничен восемью попытками, двойная постановка запрещена флагом `Queued`, исчерпание бюджета даёт видимый отказ с причиной, а `InvalidRoute` и `SessionChanged` остаются терминальными — повтор их не исправит. Проверено блоком `busy:` в `NetDM.SmokeTests`.

## 19i. Присутствие доступно из игры

`netrun_presence` (`enter`, `move`, `abort`, `leave`), поле `presence` в проекции, `travel()` и `on_presence()` в DM-клиенте, кнопки «Войти»/«Идти сюда»/«Прервать переход» в окне. Кабельная связь считается в обе стороны. Проверено: 24 теста Jest и живой `host-ipc`, где ход либо получает маршрут, либо отказывает — но не телепортирует.

## 19j. Адаптер передаёт сетевую позицию

`service_registered` запоминает `node_id` и передаёт его в объявлении хоста, поэтому дальность и маршруты стали измеримыми для реальных устройств, а не только для тестовых. Попутно исправлено: DM не поддерживает `?.` на списках — доступ к `panel["presence"]` записан как `panel?["presence"]`. Проверено живыми `netrun_adapter` и `netrun_client`.

## 19k. Медленная программа не задерживает ответы сервисов (P6)

Фоновый цикл хоста разделён на два независимых на той же частоте: ответы и публикация состояний — на одном, программы и сетевое пространство — на другом. Медленная итерация программы задерживает только следующий тик программ. Флаг сброса счётчиков стал атомарным, потому что его читают оба цикла. Проверено `check-all -Only host`.

## 27. Транспорт: P7 подтверждён тестом, P8 закрыт полосой доставки (26.11.2026)

### P7: окно уже было, проверки не было

`ServiceRuntime` держит записи инбокса до ACK и истекает их через `AckTimeoutTicks = 600` — это
60 с тика Host. Переотправка не применяет работу дважды: DM дедуплицирует по `deliveryId` и
водяному знаку `processed_through` (`netdm_services.dm`), а поздний ACK получает `Unknown`
с причиной `ack_timeout`. Всё это уже проверялось `ServiceSmokeTests`:

- `polling is repeatable until ACK` — страница не разрушается;
- `late ACK for unknown delivery`;
- `A missing ACK is Unknown` — часы сдвинуты на 700 тиков, ACK не проходит;
- `deadline expires delivery` — до доставки.

Новый код не понадобился: дефекта не было, была устаревшая запись в статусе.

### P8: полоса доставки в бюджете планировщика

`PriorityWorkScheduler` тратил один бюджет 65 мс/100 мс на все приоритеты, поэтому поток фоновых
пересчётов маршрутов мог занять окно и задержать служебную доставку. Теперь бюджет ведёт
`WorkBudgetWindow`:

| Правило | Как выражено |
|---|---|
| Доля доставки | `DeliveryBudgetMillisecondsPer100Ms` (по умолчанию 25) — её тратит только Critical/Interactive; фон останавливается на `Budget − Delivery` |
| Окно остаётся окном | Доля вырезана из бюджета, а не добавлена к нему: потолок по-прежнему 100 мс |
| Ожидание видно | `WorkSchedulerCounters.BudgetWaitsDelivery/BudgetWaitsBackground` в `/api/scheduler` и `/api/metrics` |
| Бюджет мягкий | Начатую работу никто не прерывает; ограничивается только следующее поступление |

Правило проверяется детерминированно (`CheckWorkBudgetWindow`, `NetDM.SmokeTests`): занятая фоном
доля не пускает фон, но пускает доставку; потраченное окно не пускает никого; следующее окно
открывается; доля больше бюджета отвергается конструктором; выключенный бюджет ничего не ждёт.

Проверки: `check-all.ps1 -Only host` — PASS (3 + 6 + 3 + 122 с).

### П8: полоса выключена по умолчанию — дефект найден живым прогоном (26.11.2026)

С долей 25 мс три прогона `tests/host-ipc.ps1` подряд упали на разных шагах (таймаут чтения,
`presence answered at netshell.apc2`, «the door receives the NETRUN intent as a real command»).
С долей 0 два прогона подряд — `NETDM_IPC_PASS`. Причина видна по коду: воркер проверяет бюджет
**после** того, как забрал работу из очереди, и, ожидая окно, держит слот. Когда оба воркера
ждут на фоновых задачах, интерактивная работа ждёт окна вместе с ними, хотя её доля не тронута.

Первая правка 26.11.2026 по [ADR-0009](adr/0009-budget-wait-before-dequeue.md): воркер спрашивает полосу
**до** изъятия задачи из очереди и спит без работы в руках. С включённой долей 25 мс два прогона
`tests/host-ipc.ps1` подряд — `NETDM_IPC_PASS`; но первый же полный живой набор дал **новое**
падение: `network_air_alarm` — «Датчик атмосферы не принял запрос (suspended)» (22 из 24 вместо
23 из 24; второе падение — известный `door_station`). Связь с полосой не доказана и не исключена.

Поэтому доля снова `0`, ADR-0009 **не закрыт**.

Сравнение прогонов (26.11.2026, одинаковый стенд):

| Доля | Прогон | Итог |
|---|---|---|
| 25 мс | полный набор | 22/24: `door_station` + **`network_air_alarm`** («suspended») |
| 0 | `network_air_alarm` отдельно | PASS, `clean_run.lk: True` |
| 0 | полный набор | **23/24**: только известный `door_station` |

То есть падение атмосферного теста коррелирует с включённой долей и проявляется только в
последовательности тестов, а не изолированно. Направление разбора: `suspended` — это состояние
запроса на стороне DM после отказа/таймаута, и полоса могла сдвинуть момент ответа на десятки
миллисекунд. Прежде чем включать долю, нужно воспроизвести пару «с полосой → падение, без
полосы → нет» ещё раз и найти конкретный запрос, который уходит в `suspended`.

Разбор дошёл до причины. `suspended` — это **состояние присутствия в сете��ом пространстве**, а не
статус сервиса:

- `src/NetDM.Host/Diagnostics/NetworkSpace.cs:341` ставит `presence.State = "suspended"`, когда
  оператор закрывает окно (Р6: «свёрнутое» присутствие, конец через 5 минут);
- `NetworkSpace.cs:450` (`Describe("suspended", presence)`) и `:665`
  (`refusal = presence.Moving ? "moving" : "suspended"`) возвращают этот статус в ответе;
- DM только показывает его (`network_space.dm:1122`), литерала `"suspended"` в DM нет.

То есть атмосферный запрос пришёл на **свёрнутое присутствие** и получил законный отказ. Полный
набор идёт после теста, который закрывает окно; при включённой полосе планировщика темп сдвигается,
и `network_air_alarm` застаёт присутствие ещё свёрнутым. Это дефект жизненного цикла теста/присутствия,
который полоса лишь обнажает, а не создаёт.

Следствие: ADR-0009 можно включать после того, как запрос к свёрнутому присутствию будет либо
разбудить его (`enter`/`resume` на первом запросе), либо тест будет явно входить перед проверкой.
Правило полосы при этом остаётся верным.

Уточнение по причине: `Settle()` сворачивает присутствие по пяти причинам — `host_unreachable`,

## 24. Найдено, но не исправлено: оптимистичное сообщение окна

Живой тест показал дефект, который раньше маскировался: `execute`, `import_program`, `life` и `travel` **сразу** пишут в `notice` бодрое «Действие отправлено», «Создаю ядро…», «Вхожу на терминал…» — то есть окно выдаёт намерение за результат, ровно тот класс «фиктивного успеха», который запрещает документ. Тест ждал непустой `notice`, поэтому «проходил» на оптимистичной строке, а не на решении Host.

Наблюдения из живого мира, полученные после того, как тест стал ждать реального ответа:

| Шаг | Ответ Host |
|---|---|
| создание ядра | `Ядро: active, целостность 100, поколение 1` — ядро действительно создаётся |
| вход | сначала `Сеть отказала: invalid_request` — клиент не передавал `identity`, хотя модуль требует её для всех действий |
| вход после исправления | `Присутствие активно` — вход работает |
| ход | `Нет присутствия` — клиент читает устаревшую проекцию, потому что панель не обновлялась после входа |

Нужный набор правок (проверен по частям, но не доведён до зелёного дерева):

1. `var/pending` в клиенте; `execute`/`life`/`travel` ставят `pending = TRUE` и **не трогают** `notice`; обратные вызовы сбрасывают его и пишут решение.
2. `travel(enter)` передаёт `identity` из ядра — иначе Host отвечает `invalid_request`.
3. Клиент запоминает `identity` из последнего ответа, чтобы ход не зависел от устаревшей проекции.

### Исправлено (26.11.2026)

| Правка | Результат |

| Оптимистичные сообщения убраны: окно пишет только решение Host | «Действие отправлено», «Создаю ядро…», «Программа отправлена», «Иду к цели» удалены |
