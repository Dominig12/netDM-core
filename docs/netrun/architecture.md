# Целевая архитектура NETRUN поверх NETDM

Документ фиксирует **принятую** архитектуру и отклонения от буквы §3 спецификации с обоснованием. Решения — [adr/](adr/), факты о текущем коде — [t0-audit.md](t0-audit.md), состояние — [status.md](status.md).

## 1. Слои и направление зависимостей

```text
BYOND / DM            физическое состояние, mind, игровые обработчики
TGUI / PixiJS         отображение, ввод, локальная анимация
        ↕ bounded IPC (named pipe / UDS) + нативный shim
NetDM.Host            единственный процесс = composition root
  ├─ NetRun.Content     контент: пресеты, агенты, локации, R&D, мессенджер
  ├─ NetRun.Observability  проекции игроку, телеметрия, диагностика
  ├─ NetRun.Runtime     IR, VM, планировщик, долгие операции
  ├─ NetRun.Core        хосты/сущности/ресурсы/права/действия/эффекты/мир
  └─ NetDM.Services     схемы, каталог, подписки, команды, доставки
     NetDM.Core         топология, маршрутизация, транспорт, политики
```

Правила направления:

1. `NetDM.Core` не знает ничего о NETRUN и о DM.
2. `NetDM.Services` знает только транспортные контракты; игровой контент туда не добавляется.
3. `NetRun.*` зависят от `NetDM.*`, но не наоборот.
4. Только `NetDM.Host` (composition root) ссылается и на транспорт, и на NETRUN, и собирает зависимости.
5. Интеграционные адаптеры (DM ↔ Host) живут на границе: DM-адаптер в MOLOT, C#-адаптеры — в `NetDM.Host/Transport`.

**Отклонение от §3 (ADR-0001):** процесс по-прежнему называется `NetDM.Host`, а не `NetRun.Host`. Переименование исполняемого проекта ломает `deploy/bluemoon/Host.Dockerfile`, Windows-комплект и все скрипты стенда без функциональной выгоды. Спецификация явно допускает иные имена при сохранении границ; границы соблюдены, имя проекта — историческое.

**Новые проекты вводятся по одному и только когда в них появляется содержимое.** На этапе N1 существует `NetRun.Core`; `NetRun.Runtime`, `NetRun.Observability`, `NetRun.Content` создаются на этапах, где в них появляется код (см. [roadmap.md](roadmap.md)). Пустых проектов «на будущее» не создаётся.

## 2. Владение состоянием

| Данные | Авторитетный владелец | Где |
|---|---|---|
| Физические объекты, питание, повреждения, персонаж/mind | DM | MOLOT |
| Узлы, рёбра, маршруты, передача, ограничения транспорта | NETDM | `TopologyStore`, `SharedMediumNetwork`, `RadioPacketTransport` |
| Схемы, каталог сервисов, подписки, доставки, application-ACK | NETDM | `ServiceRuntime` |
| Цифровые хосты, компоненты, программы, сущности | NETRUN | `NetRun.Core` |
| Права (capability grants), отзыв, fencing | NETRUN | `CapabilityAuthority` в `NetRun.Core` |
| Виртуальные ресурсы (CU, RAM, Storage, Bandwidth) и leases | NETRUN | `ResourceLedger` в `NetRun.Core` |
| Действия, эффекты, их стоимости и cooldown | NETRUN | `ActionRegistry`, `EffectRegistry` в `NetRun.Core` |
| Предметная информация R&D/карго/медицины | Конкретный игровой сервис, один источник записи | Этап N3 |
| UI и кеши | Производные проекции | `NetRun.Observability`, TGUI |

**ARCH-001:** на каждый инвариант одна точка изменения. Пример: стоимость и cooldown действия известны только `ActionRegistry`; UI и скрипт получают их из дескриптора и не могут их переопределить.

**ARCH-003:** `NetRun.Core` — один логический writer на домен. Все мутации проходят через публичные операции владельца, рабочие потоки получают версионированный снимок и возвращают намерение. `ConcurrentDictionary` и одиночные `lock` не используются для защиты составных инвариантов.

## 3. Модель цифрового хоста

Хост — композиция типизированных компонентов, не наследник общего класса:

| Компонент | Данные |
|---|---|
| `NetworkComponent` | связанные узлы графа, интерфейсы (wired/radio), принадлежность домену |
| `ComputeComponent` | ёмкость буфера CU, скорость CU/с, текущий буфер, спрос |
| `MemoryComponent` | слоты RAM, размещённые процессы |
| `StorageComponent` | объём хранилища и файлы |
| `SecurityComponent` | политика доступа, разрешения, состояние тревоги |
| `ServicesComponent` | опубликованные контракты (instance, тип, версия) |
| `ProcessesComponent` | исполняемые экземпляры программ |
| `PresenceComponent` | размещённые активные сущности |
| `LifecycleComponent` | питание, повреждения, доступность, поколение |

Компонент отсутствует — возможности нет. Шлюз без `ComputeComponent` не может хостить программу; APC без `PresenceComponent` не размещает личность; Relay без `StorageComponent` не хранит файлы.

## 4. Конвейер действия

```text
1 Validate      контекст, право, тип цели, наблюдаемость, предусловия
2 Reserve       атомарное резервирование CU/RAM/слотов, проверка cooldown
3 Dispatch      локально или через NETDM (маршрут + политика сервиса)
4 TargetCheck   конечный владелец проверяет поколение, состояние, fencing права
5 Commit        авторитетное изменение у владельца
6 Finalize      учёт затрат, освобождение резервов, событие, результат обратно
```

Состояния операции: `Created → Preparing → InTransit → Executing → Committed | Completed`, до commit допустимы `Cancelled`/`Failed`, после commit отмена не откатывает эффект. Клиент может получить `UnknownOutcome` при потерянном ответе (SVC-002).

## 5. Ресурсы

`buffer(t+dt) = clamp(buffer(t) + max(0, rate - demand) * dt - committedCost, 0, capacity)`

Восстановление начисляется один раз за интервал монотонного игрового времени (`ISimulationClock`), независимо от FPS и wall clock. Резерв имеет владельца, срок и идемпотентный release. Провайдер не может выдать больше ёмкости; удалённый lease перестаёт учитываться через grace period после потери маршрута.

## 6. Права

Разделены `Identity` (кто), `Presence` (где), `Principal/Actor/Process` (от чьего имени) и `Capability` (что разрешено). Права программы — пересечение выданного, действующего у делегирующего и политики цели. Категории `Discovery, Communication, Read, Control, Execution, Administration` не образуют лестницу.

Каждый grant имеет версию (fencing). Проверка выполняется на границе commit; grant с версией ниже текущей для (субъект, цель, категория) не авторизует операцию. Отзыв, упорядоченный до commit, блокирует действие.
